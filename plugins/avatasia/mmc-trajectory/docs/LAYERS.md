# 前端分层：这个页面的功能类型 → 层 → 归属

这份文档对应的是一类**已经付出过代价**的错误，不是风格偏好。下面每一条「代价」都能在本仓库里指到具体代码或具体缺陷。

## 0. 要解决什么

症状是「功能不断堆叠，联动时出现异常」。拆开看是两件事：

1. **堆叠**：新控件被放到「离它作用对象最近的地方」，而不是「离它所属的层最近的地方」。于是同一层的控件散落在页面的两处。
2. **联动异常**：没有分层的共享模型，每加一个跨控件的能力，就只能在各个渲染函数里手写互斥分支。分支之间必然互相看不见对方在做什么。

第 2 点是重点。上一轮修的三处异常轴缺陷——合计指向另一个选择、`重置` 在多选下自称已是默认、单选说「已叠加 4 条规则」——**没有一处是算错**，三处都是「两个筛选器各自推理自己」的症状。它们的共同根因只有一个：筛选这件事在这个页面里没有一层。

## 2. 已经付过的代价

### D1 — ~~同一层的控件被劈成两半~~ **设计如此，不是缺陷**

**这一条撤回。** 它曾经被写成需要偿还的结构债，理由是「看哪些记录」这一个职责住在文档位置 3（`form.toolbar`）和位置 5（`.filter-sticky`）两处、中间隔着 KPI 区。

**这个判断是错的。** 查询条件是一个**聚合**，不是一个控件：前端 UI 与最终请求参数本来就该拆开，两块甚至更多块 UI 各拼一部分参数是正常形态（是否 MVVM 与此无关）。要求它们在文档里连续，是把「层要连续」当成了设计洁癖，而它不是——KPI 区答的是「这场会话一共发生了什么」，筛选区答的是「我现在看其中哪些」，两者本来就不必挨着。

当时提的搬动方案（把搜索框和时间区间移进 sticky 筛选带）也被否决：**窄屏上 sticky 会占满视口，可用区域反而更小。** 搜索框尤其如此。

所以这一条留在这里，是为了让下一个读到这里的人知道**这条路已经走过、结论是不动**，而不是把它当成待办。

真正该盯的不是控件在文档里的位置，而是**位置变了之后由谁负责重算**——见 D9。

### D2 — 同一份 state 里，有两句互相矛盾的设计声明

**已修（Stage 2-c）**，原文保留如下以说明修的是什么。

```js
// kinds
// The type chips are the only filter, so this array is the only definition of what is on
// screen.

// rangeFrom
// This is the one filter the KPI follows. The type chips and the search box narrow
// what is *drawn*; a range answers a different question …
```

两句话都对，各自描述的是一个**更早的**页面。合起来，这个对象对「筛选是什么」给出了两种互不兼容的模型。这不是笔误，是堆叠留下的沉积：**没有一层来裁决哪句话作废。**

`README.md` 其实已经把这件事说对了一半——它写的是「the only filter **over kinds**」，并明确说明时间区间与异常筛选是横跨类型、且不改写 `kinds`。带限定词的那句现在仍然成立；代码注释里**没有限定词**的那句不成立。分层不是要推翻 README 的模型，是给它一个归属：**层不新增字段，只是命名谁拥有它们。**

### D3 — 汇总层用了筛选层的视觉语言

`kpiStats()` 只跟时间区间（`hasTimeRange() ? scopedStats() : payload.stats`），不跟类型轴、不跟搜索、不跟异常轴——即 KPI 讲的是「这一段时间里的整场会话」，而它的卡片和筛选控件共用同一套视觉语言、同一个滚动流里的相邻位置。读者无法从视觉上知道这两者口径不同。

### D4 — 跨层回写没有声明

全页唯一一条「从下往上写」的数据流是总览条的区间刷选 → `rangeFrom/rangeTo`，以及它自带的「清除区间」「更新到最新」。它写的是 L2 的字段，但持有者是 L3 的控件，而且 `overviewSelection` 另存了一份区间。没有声明，于是每次动它都要重新推演谁该刷新。

### D5 — 一个字段多个写者 **部分已做（异常轴已收敛，基础轴未动）**

原文记的是：`state.kinds` 4 处写入、`state.anomalyRules` 4 处、`multiAnomaly` 3 处、`query` 3 处、`limit` 3 处。互斥不变量只能靠一个协调函数 `resetBaseFilters()` 去维持，而协调函数本身就是「没有共享模型」的产物。

**Stage 2 之后重新数过（2026-10-12，`index.html` 当前值；`kinds` 与 `overviewSelection` 那一列在本轮第 9 项之后再数了一次）：**

| 字段 | 写者 | 读者 | 状态 |
| --- | --- | --- | --- |
| `state.anomaly` | **2**（都是 `= defaultAnomaly()` 整体赋值） | 36 | **已收敛**：一个字段、一个工厂、每键一个写者 |
| `state.kinds` | **3 直接 + 1 委托**（四条控制路径，`清除筛选` 改为调用 `resetBaseFilters()`） | 15 | 未动 |
| `state.query` | 3 | 4 | 未动 |
| `state.overviewSelection` | **4**（两个「清空」路径已收敛到 `dropOverviewSelection()`） | 4 | 部分进展，离 R5 还差三个（R5，见 Stage 3） |
| `state.limit` | 2 | 12 | D13 顺带从 3 降到 2 |

所以这条**仍然没有整条关闭**：异常轴那半已经交出去了；基础轴那半的**「默认值只有一份」拿到了**，`state.base` 那个命名空间按 codex 的排序显式放在最后。`resetBaseFilters()` 这个协调函数还在——它现在是**唯一**的基础轴默认值写者，而不是两个平行函数各写一遍。见未做清单第 9 行。

### D6 — 控件的位置和它写入的层不是一回事

窗口控制（`显示最新 200 / 显示全部 / 向上加载`）在**列表面板里**，但它写的是「渲染多少」这一层的事，不改筛选结果。同类还有总览条：它既是投影，又持有写入筛选的控件。位置即归属的直觉在这里已经不成立，而文档里没有一处声明它。

### D7 — 函数名跨层

`applyFilterScope()` 的名字说的是 L2（筛选作用域），函数体第一行却是 `if (!dom.kpiScope) return;` —— 它写的是 L4 的口径行。真正的作用域处理（异常模式下把 `[data-filter-scope]` 标 inert）在 `syncAnomalyMode()` 里。

一个以 L2 命名、只写 L4 的函数，会让下一次读代码的人把口径声明当成筛选行为的一部分。这不是笔误级的问题：它是 D4 的同一个根因——**跨层关系没有被声明，于是命名先替它做了个假声明。**

### D8 — L6 读的是「整场会话」，不是「表里有什么」 **已修**

L6 检视面板该读 L5（列表），实际读的是 L0：`selectedRecord()` 和 `revealSelection()` 扫的是 `state.flat`——未经筛选的整场会话；而 L5 的行是拿 `visibleEntries()` 建的。两边对「选中」的定义不是同一个。

读者看到的是：选中一条记录 → 点「工具失败」→ 账本从 61 条变成「已显示 2 条」，检视面板纹丝不动仍显示原来那条，而且**表里没有任何一行带选中标记**。页面内部没有任何一处自相矛盾——只是面板在描述一个屏幕上看不到的东西。

更糟的是能点的按钮也一起撒谎：`复制 JSON`、`交给 AI 分析这条` 读的是同一个旧记录。

唯一能回收 `state.selectedId` 的地方是 `applyPayload()`，而且只在**数据签名变化**时。本地改筛选一次都不走那里，所以没有任何一条筛选轴能救它。

**修法**：判定权收进 `revealSelection(entries)` 一个函数，参数就是 L5 即将拿去建行的那个数组；调用点收进 `renderLedger()`——所有会改变「表里有什么」的路径的**唯一出口**（9 处直接调它，其中就包括类型轴本身）。`selectedRecord()` 降级成纯查找，它的 5 个读者（面板 / 复制 / 交接 / 交接按钮 / …）不再各自重新回答「什么算选中」。守卫：`tests/verify-selection.mjs` + `tests/mutate-selection.py`。

### D9 — 钉住偏移的重算责任只挂在一根线上 **已修**

四个 sticky 层的偏移由 3 个 CSS 变量串起来，唯一写手 `syncStickyOffsets()` 的唯一调用点是 `render()` 末尾。而 `renderLedger()` 被 9 处**直接**调用绕过 `render()`（类型轴、搜索、总览刷选、加载更早、窗口模式、选中行…）。今天这 9 处恰好都不改 band 高度所以看不出来——**不变量靠约定撑着，不靠结构**：再加一个条件时照这个写法走，就会静默错位。

同时没有任何 resize 挂钩（无 `resize` 监听、无 `ResizeObserver`）。而稳定会话下每次轮询都是 304，`render()` 根本不跑（304 分支只在 `state.loading` 时才 render）——窗口一变窄、类型行换行、band 长高，**永远没人重测**。

**修法**：测量收进 `renderLedger()` 出口（与 D8 同一个出口），`render()` 里不再重复调；补 `resize` 挂钩，按 `requestAnimationFrame` 合并成一帧一次（每次测量读 3 个 `offsetHeight`，会强制布局，拖窗口时逐事件测量就是布局抖动）。守卫：`tests/verify-sticky.mjs` 新增 5 条断言 + `tests/mutate-sticky.py` 新增 7 条变异。

> 顺带说明 D1 与 D9 的关系：D1 说的「层被劈开」是**位置**问题，结论是不动；D9 说的是**位置变了之后由谁重算**，这才是真问题。两者不要混。

### D10 — 每轮轮询把整个 lineage 重读重解析一遍 **已修**

这一条不在前端，在 L0。`handleTrajectory()` 命中 `trajectoryCache` 时直接短路返回（好）；**未命中时**那个循环（`server.mjs:1881-1919`）对 lineage 上**每一个** generation 文件做 `readHead()` 全量读 + `parseMessagesJsonl()` 全量解析，然后重建全部 row。

而 `trajectoryCacheKey()` 把每一代的 `byteLength` 拼进了键，所以**只要会话还在追加，键就变，就必然 miss**——缓存是全有或全无的。

本机实测（会话 `mvs_2fd90165…`，23 代）：

| | |
| --- | --- |
| 每轮读入的源字节 | `payload.session.sizeBytes` = **99,986,501** |
| 其中冻结的 snapshot（22 个） | 99,889 KB = **99.90%** |
| 只有 `messages.jsonl` 在长 | 97,526 字节 = **0.10%** |
| 重建耗时 | **1,138 ms**（拟合 31 ms/MB） |
| 占 2,500 ms 轮询间隔 | **46%** |

同一份数据在三个层各自独立地表现出同一个比例：**服务端输入 99.90% 冗余、线上字节 99.99% 冗余（5 分钟 1.31 GB 换 118,875 字节真实新增，放大 11,006×）、页面解析 ~99.99% 冗余**。会话在忙碌时每 3–6 秒变一次，而轮询每 2.5 秒问一次——所以**几乎每次轮询都撞上全量重发**。

**曾被考虑并否决的两条**：

- **响应开 gzip**（36.0 MB → 7.8 MB，4.6×）。实测**净亏损**：同机 loopback、同样 `await response.json()`，裸传 201 ms vs gzip 268 ms，页面反而慢 67 ms；服务端每个 cacheKey 还要多付 458 ms deflate，浏览器付 80 ms inflate。**本机不是带宽瓶颈，压缩换不来东西。**
- **缓存每代的序列化片段**（用字符串而非对象图，内存友好）。**不成立**：`buildTrajectoryPayload()` 里 `turn.index = turns.length + 1` 是**全局序号**，且同一个 `turnId` 会跨代出现（`turnById` 复用该 turn 并继续追加记录）。所以每一代既不能独立缓存也不能独立拼接。

**修法**（四问）：

1. **归层** — L0，服务端。第二个缓存，与 `trajectoryCache` **并列而非替代**：整场缓存在命中时仍直接短路，新缓存只在整场 miss 后才被读写。**互斥由控制流保证**，不靠约定。
2. **关联** — 新缓存按**单文件**粒度，键与整场缓存不同，两者互不写入对方的键。不新增任何前端 state，不改任何页面行为。
3. **布局** — `start()` 闭包内、`trajectoryCache` 旁边。**不做模块级 Map**（跨 `start()` 泄漏）。自带按**字节预算**的 LRU，默认 256 MB。
4. **口径** — **不改变任何对外承诺的数字**。唯一要守的不变量：**缓存命中必须产出与冷读逐字节相同的 body**。守卫 `tests/verify-parsed-rows.mjs` 断言这一点。

**缓存键的三个正确性前提**（任一条错了，缓存就会供出陈旧数据——这是它唯一不能出的错）：

- **键用 `filePath` 而不是 `fileName`。** `messages.jsonl` **不是唯一的**，每个会话都有一个；只用文件名，两个会话的同名文件可能撞车。
- **键用 `stat` 的 `size` + `mtimeMs`，不用 catalog 里的 `byteLength`。** 代码自己在 `server.mjs:1889-1894` 注释了那个值是快照、会过期，而且 active 文件每轮都在它之外继续增长。
- **键含 `limit`。** `readHead` 会按 `limit` 截断，截断与否是读出来的事实的一部分，缓存值里带着 `truncated` 判定。

**共享带来的写入风险**：`rows` 跨请求共享同一批对象。已逐个查过下游——`redactStructure()` 构造新对象（`out = {}`）而不原地改，`record = { ...base }` 也是新建，`splitRawRecords` 改的是新建的 record。唯一写缓存对象的是 `row[ROW_GENERATION] = link.generation`，而同一 `filePath` 恒定映射同一 generation，幂等。

**内存代价（实测，不是估计）**：`JSON.parse` 保留率实测 **1.36×**（34.3 MB 文本 → 46.7 MB 堆），且这是**下限**——payload 已被 `splitRawRecords` 剥掉消息正文，真实的 rows 图更大。外推到 95.4 MB 源文件是 **130–290 MB 常驻**。所以上界必须显式：换掉的是每 2.5 s 约 350 MB 的分配 churn，换来一次性常驻。**预算按字节而非条数**，因为条数与体积无关（一条可能是 40 字节也可能是 40 MB）。

> 真正把这件事做干净的是增量协议（`?since=`，服务端只发新增尾部）。它连这 130–290 MB 都不需要，而且额外消掉那 139 ms 的 `JSON.stringify` 和页面的 200 ms 传输+解析。**按代缓存胜在不动协议**，性能上它被增量协议严格支配。这一条留作后续。

### D11 — 为「量一下大小」把整场消息体序列化一遍，然后扔掉 **已修**

D10 修完之后实测发现重建时间没动，于是回头查 D10 的成本拆分，发现 D10 里写错了一个数。实测（真实 22 个冻结文件）：

```
冷读（读 + 解析全部）  306 ms      ← 不是我在 D10 里写的 ~1,000 ms
命中缓存                 2 ms
解析吞吐              311 MB/s
```

**更正 D10**：读+解析约 306 ms，不是约 1,000 ms。当时那个数是用「1,138 − 139（stringify）」减出来的，把没有查过的 `buildTrajectoryPayload` 和 `buildRawPayload` 一起算进了「读+解析」里。按代缓存的真实收益是**约 300 ms，占一轮重建的约 21%**，不是 3.5×。常驻堆实测 **116 MB**（95.3 MB 源文件 × 1.22×），低于当时 130–290 MB 的外推。

> 顺带修了 D10 自己发的代码里的一个缺陷：预算代理写成 3×，于是 95.3 MB × 3 = 286 MB 计费压过 256 MB 预算，LRU 把放得下的条目也赶走了。实测保留率 1.22×，代理改为 2×。**预算的好坏完全取决于这个数**。

剩下的 ~1,100 ms 在下游，其中最大的一块是个纯浪费：

`buildRawPayload(message, redact)` 对**每一条记录**执行 `JSON.stringify(message)`——18,337 次、合计约 100 MB——只为回答两个问题：序列化后是否超过 `MAX_RAW_BYTES`（65536），以及是否含 `.minimax` 需要脱敏。**那个字符串用完就扔**：`splitRawRecords()` 在最终序列化之前把 `raw` 从每条记录上摘掉（`server.mjs:1954` 的注释自己写着「from here on the body carries no message bodies at all」），而 `raw.value` 真正带走的其实是**原消息对象**，不是这个字符串。

于是每一轮重建都要把 100 MB 消息体完整序列化一遍、量一下、再扔。而 `raw` 只有打开某条记录的原文页、复制、交接时才读得到——18,337 条里几乎从不读。

**修法**（四问）：

1. **归层** — L0 服务端。`raw` 的计算从「构建 payload 时」移到「`/raw` 被请求时」。不新增任何 state,不改筛选/渲染层。
2. **关联** — `raw` 与 bulk payload 的关系不变(它本来就不在 bulk 里)。变的是**判定「过大」的时机**:从构建时移到请求时,两者必须在同一处写,不能一个函数判、另一个函数用。
3. **布局** — bulk payload 仍然不带 `raw`;`/raw` 仍然按 record index 服务。**新增的只是一个定位符**:每条记录记下它来自 `rows` 的第几条,由 `splitRawRecords()` 摘进缓存项,`/raw` 用它回到那一条消息。`handleRaw()` 再调用 `buildRawPayload()`——一次只算一条。
4. **口径** — **`rawOmitted` 从 bulk payload 迁到 `/raw` 响应**。这是本项目第一次做**契约级**的口径变更,所以逐个读点列在这里,并在 `tests/verify-raw-lazy.mjs` 里逐个加断言:

### D13 — 检视面板能改窗口，于是「已显示 200 条」在一秒内变成 15,224 条 **已修**

**现象**：在「显示全部」下选中一条早期记录，点「显示最新 200 条」，那条记录离开窗口，表里再没有行带选中标记，**但检视面板还在描述它**。

**根因**不是漏了清空，是 `revealSelection()` 在**切片之前**判定，并且会 `state.limit = Math.min(needed, entries.length)` —— 它主动把窗口撑大到能装下那条选中：

```
点下「显示最新 200 条」
  此刻窗口条   已显示 200 条
  下一秒       已显示 15,224 条      ← 差值 15,024 = 选中记录在 matched 里的位置
```

读者自己点的按钮把窗口条上的数字改了，而且是在点击之后才改。

**两条错**：

1. **窗口成了检视面板能写的东西。** `state.limit` 因此有两个写手（窗口控件 / 一次判定），这正是本文件里每一个双写手缺陷的形状（R1）。
2. **判据错了。** 「读者能看见什么」是**窗口**，不是筛选结果。判在 `matched` 上，一条通过了全部筛选、却被窗口切掉的记录会继续留着选中。

**修法**：`revealSelection(entries)` 收成纯谓词——只写 `state.selectedId`，不再碰 `state.limit`；调用点从切片前挪到切片后，参数从 `matched` 改成 `windowed`。窗口收窄到不含选中记录时**取消选中**，不撑大窗口：读者的窗口选择优先于更早的那次点击，且与筛选轴的既有规则一致（记录被滤掉即取消选中）。

**口径变更，读点已逐个改**（`tests/verify-selection.mjs` 整份重写，14 断言）：

| 旧承诺 | 新承诺 |
| --- | --- |
| 「窗口会被拉到选中所在处，按表计数」（`limit === 8`） | 「选中在窗口之下时取消选中，且窗口原地不动」（`limit === 3`） |
| 判定发生在切片**之前** | 判定发生在切片**之后**，参数是 `windowed` |
| —— | 新增：`revealSelection` 源码里不允许出现 `limit` 这个词 |

`tests/mutate-selection.py` 里有**两条变异是改写而不是删除的**：原来的「窗口不会被拉到选中」守的正是现在删掉的那行 `state.limit` 写入，它现在改为弄坏替换它的新规则；原来的「判定发生在切片之后」守的是相反的顺序，现在改为弄坏「判定用的是窗口而不是筛选结果」。

### D14 — 在途建行被取代时跳过 `restoreRowAnchor()`，滚动位置永久丢失 **已修**

**归层** L5 的建行路径，但**归属的规则是 D9**：滚动位置只能由 `restoreRowAnchor()` 这一个出口决定。它写的是 L5 的什么状态？一个还没有的字段——修法需要新增一个（见下）。

**关联** 与 `ledgerBuildToken` **从属且同源**：D12 引入 `ledgerBuildToken` 是为了让在途分批「就地退出、不碰 DOM」，那条规则是对的，坏的是退出时顺手把 D9 的还原也一起跳过了。与 `firstVisibleRow()` / `anchorOffset()` 并列，是锚点三件套的第四个成员——它管的是**跨建行的意图**，不是单次测量。

**布局** 不新增 DOM、不新增面板。纯 JS：一个模块级变量 + `renderLedger()` 里一处赋值 + `restoreRowAnchor()` 里一处清空。

**口径** 不改变任何已有数字。「显示全部」仍显示全部；窗口条读数不变；选中语义不变。可观察变化只有一条：滚动位置不再丢失。

**实测（19,626 行 / 155 轮 / 文档高 716,000 px / 视口 841×900 / 已发布代码无探针）**：

`renderLedger()` 在 `clear(ledger)` 之前捕获 `{anchor, scrollY}`，这一点是对的。问题在 `clear(ledger)` 的副作用：

```
clear(ledger) 之前   doc = 716,016 px    scrollY = 715,080
clear(ledger) 之后   doc =    1515 px    scrollY =     616   ← 文档塌了，浏览器把 scrollY 夹到底
建行 6 帧，约 3,956 ms，期间 scrollY 停在被夹住的位置
buildStep() 收尾     restoreRowAnchor() 把位置算回来
```

所以位置**不是丢失，是被摧毁再重建**——中间那 3,956 ms 里读者看到的是第 1 轮。`restoreRowAnchor()` 本身完全正确，从被夹住的 2,051 出发也能算出 `delta = +103,559` 落回 105,610。

**真正的丢失点是 `buildStep()` 的提前 return：**

```js
function buildStep() {
  if (build.token !== ledgerBuildToken) return;   // ← 这一句把 restoreRowAnchor() 也跳过了
  ...
  restoreRowAnchor(anchor, scrollY);
}
```

D12 给在途分批定的规则是「就地退出、不碰 DOM」——退出得对。但退出时**没人把滚动位置交还给下一个建行**，而下一个建行捕获锚点时读到的是已经被夹断的位置：

```
cap  ySave=715080 yReal=616 doc=1515     ← 轮询建行开始，位置被摧毁
     （无 rst：这次建行被点击取代，restoreRowAnchor 从未执行）
cap  ySave=5530  yReal=1065 doc=1965     ← 点击触发的 renderLedger，锚点已经错了
rst  after=-15 delta=0 yIn=5530 yOut=5530
     docYWas=5515 docYNow=5515           ← 忠实地还原到了一个错误的位置
```

一旦落到顶，之后每一轮都拿「第 1 轮」当锚点，**自我维持**，读者再也回不去。

**触发面**：任何在轮询建行途中直接调用 `renderLedger()` 的读者动作。最大的一处是 `selectRecord()`——**点任意一行都会整表重建**。「显示全部」下建行 3,956 ms、轮询 2.5 s，所以点一行大概率落在建行途中。

**对照组（证明与 `content-visibility` 无关）**：在无 `content-visibility` 的已发布代码上，点行时**没有**建行在途，则 `rst` 为 `delta 0 / yIn = yOut = 105,494`，位置纹丝不动。同一份代码、同一处点击，唯一变量是「有没有建行在途」。

**修法**：把「读者想去哪」从「建行结束时算」提前成「第一次捕获时记下，此后每次建行转交」。一个模块级字段 `pendingAnchor`，一个写手 `forgetScrollAnchor()`：

- `renderLedger()` 只在 `pendingAnchor` 为空时捕获 `{row: firstVisibleRow(), y: window.scrollY}`，之后每一趟都沿用；空的那一趟才读实时位置。
- `restoreRowAnchor()` 第一句就是 `forgetScrollAnchor()`——它是唯一以「还原」结束一链的地方，所以也是唯一必须消费它的地方。
- 五条提前返回（加载中、硬错误、无 payload、无会话、无命中）各调一次 `forgetScrollAnchor()`：它们把账本换成一个状态块，没有可锚的行，**丢弃而不是还原**——否则会把一个针对旧会话或旧筛选测出来的位置，套到另一个上面。

**顺带修掉的**：`ledgerBuildToken += 1` 从 `applyFilterScope()` 那一侧移到 `clear(ledger)` **之上**。这不是顺手，是上面那条的前提——四条提前返回都在自增之前返回，它们同样清空账本，却什么都不退休，于是在途建行会继续往骨架屏里追加轮组，随后还会拿一张已经不存在的表的锚点去移动页面。现在自增在清空之前，四条返回路径和正常路径走的是同一句。

**守卫**：`tests/verify-anchor-carry.mjs`（10 条断言）。捕获那三句是**跑**出来的——`firstVisibleRow()` 与 `window.scrollY` 换成返回**另一个**位置的桩，一个每次重读的版本会给出桩的答案而不是预设的答案；消费者则按条数点，`clear(ledger)` 到 `var groups =` 之间的 `return;` 必须和 `forgetScrollAnchor()` 一一对应。`tests/mutate-anchor-carry.py` 6 条变异全捕。

`mutate-ledger-batch.py` 里原有两条变异锚在 `ledgerBuildToken += 1;` 后面那一行上，自增移动后失效——**已重新锚定到 `clear(ledger);`，一条未删**，并新增一条「把自增放回提前返回之下」忠实复现本条缺陷。`verify-ledger-batch.mjs` 相应从「数一次自增」加强为「数自增与 `clear()` 之间的 `return;`」——原来那条断言对四条提前返回完全失明。

**浏览器实测（本机，19,991 条 / 156 轮 / 视口 841×900）**：显示全部 → 滚到第 133 轮 / #17188 → 点一行 → 等重建。建行途中视口短暂塌到第 51 轮（预期内，文档正在重建），**建行收尾后回到第 134 轮 / #17207**，正是点行前那一行（会话实时增长，序号整体前移）。再点一行，仍在第 134 轮 / #17215，被点的 #17226 带选中标记。修复前同一操作把读者永久留在第 1 轮。

### D17 — 运行时只给自己看的结算记录，被当成消息渲染成一行空白 **已修（2026-10-12）：保留记录，改成可筛**

**症状**（2026-10-12 用户报）：「#22501 这条消息是什么意思？为什么是 system。回复不应该是最后一条消息么？」

账本上每一轮回复**后面**都多挂一行空白的「系统」。翻记录，全会话 **19 行**，跨 turn 1 → 168、10-10 → 10-12：

**它是什么**——运行时里有一个专用工厂，`app.asar`（未压缩）内 `task-read-settlement.js`：

```js
export function createBackgroundTaskReadSettlement(timestamp) {

             display: false, details: { version: 1 },
             hostMetadata: { providerVisibility: 'omit' }, timestamp };
}
```

一条刻意为空的记录：内容空、给 `display: false`、标 `providerVisibility: 'omit'`。

**三个「不要给人看」的信号，逐个核实的结果不一样**——这一条改正了我最初的说法：

| 信号 | 核实方式 | 结果 |
| --- | --- | --- |
| `providerVisibility: 'omit'` | `isHostOnlyMessage()` → `projectAgentMessagesForModel()` | **真的强制**：`messages.filter(m => !isHostOnlyMessage(m))` 是该函数第一步，在 `convertToLlm()` 之前。这些记录确定不会发给模型 |
| `display: false` | 全 asar（395,844,226 字节）搜 `display === false` | **0 处命中**。`display` 只被 `appendCustomMessageEntry()` 写进条目、被 `createCustomMessage()` 原样读回，**没有任何一处拿它过滤** |
| `content: ''` | payload 实测 | 确实空，渲染成空白行 |

**所以不能说「我们违反了运行时的强制规则」**——`providerVisibility` 那条确实强制，`display` 那条**运行时自己都没执行**。这一点必须写清楚，否则下一个读者会以为照着 `display` 写过滤是在遵守一条已存在的规则。

**那它还算不算缺陷？算，但理由要换成站得住的那条**：

1. **一行没有任何内容的行不是一行。** 它不告诉读者任何事，却占位、参与计数、出现在「回复之后」——正是它让「回复应该是最后一条」看上去不成立。
2. **同一个文件里已经有先例，而且理由一模一样。** `server.mjs:1203-1207` 写明：`compactionSummary` 之所以要自己的 kind 而不是混进 `system`，是因为「客户端只按 kind 过滤，混进去就没法单独保留或丢弃」。`background_task_read_settlement` 是同一类记录——运行时写的、非对话的。
3. 归 `system` 还有连带代价：取消勾选「系统」时它跟着进出（这正是那条注释担心的后果）。

**为什么不能在前端解决**：payload 里那条记录的字段是 `id, turnId, role, generation, timestamp, …, kind, title, summary`——**没有 `display`，也没有 `customType`**。前端拿到的只有 `role: 'custom'` + `kind: 'system'` + `text: null`，**无法与任何其它系统记录区分**。判据只能由服务端带过来。

**影响面**：19 / 22,552 条。污染三处读数——窗口条总条数、KPI 计数、「系统」轴的进出。

**未修，而且「服务端直接不带出来」这条路已经被排除**——不是因为我偏好保守，是因为它会破坏 Stage 4 的增量协议：

`server.mjs:1003` 是 `index: records.length + 1`。**`record.index` 是对「已发射记录」的稠密连续计数，不是源文件里的行号**（源行号另存在 `rawRow`，`server.mjs:995`，`/raw` 顺着它回原始行）。所以一旦这 19 条不再被 push，**它之后每一条的 index 都会整体下移一位**——正在跑的客户端手里的 `?since=` 游标会指向一条它从未收到的记录，增量协议静默丢数据。

于是只剩一条路：**保留记录、保留 index，只是不把它渲染成一行**（沿用 `compactionSummary` 的先例给它自己的 kind，或由服务端把判据带过来让前端排除）。这仍然要动「口径」那一问：改的是「账本上有哪些行」这个承诺，而 `#window-count`、KPI 条数、异常轴计数三处都在读它。

> 排查方法备注：`app.asar` 未压缩，可直接按字节偏移搜。`display === false` 这种「字段名 + 比较」的搜法比搜 `display` 本身有用得多——`.display` 在 395 MB 里 2472 处命中，绝大多数是 `Function.displayName` 的噪音。

**一个当时没有解释清楚的观察**：某一趟近底部的重建，`postY` 比 `preY` 高了 77,226 px，而屏上的行没有变。它出现在一次耗时 7.9 s 的点行之后，随后被后续重建原样带下去。今天在同样靠近底部的深度上没有复现（`740,165` 连续六趟 `preY == postY`）。**当时记为「不写成缺陷，也不写成没问题」——2026-10-12 有了候选解释，见本节末尾「D15 自身的一个缺陷」。那个缺陷是跨重建存活的 skipping class，它会让文档塌掉再长回来，位置跳变正是这个过程的副产品。但我是在默认窗口下复测的，那次观测是在显示全部下做的，两个条件不同，所以「很可能」而不是「已解释」。**

#### D18 — 上下文代控件在会滚走的工具栏里（2026-10-12 修）

**症状**（chli 报）：「上下文代的筛选条件没有了，排查下。怎么解决。另外希望滚动的时候，能出现在 全部这行的最后面。共用一行。」

**四问**

1. **归层** — L1（选哪一段上下文），不是 L2 筛选。依据：它和「会话」是同一类控件（选哪段对话），并且它从来不带 `data-filter-scope`——搜索框和类型轴才带。

**我第一次算错了，错在漏了容器自己的内边距**

```

#### D21 — 窄视口整页横向滚动，而修法里有一半是会骗人的（2026-10-12 修）

**症状**：视口窄于 640px 时文档比视口宽，横向滚动最多 262px。**没有任何人报过这条**——它来自未做清单第 6 项（「窄屏 sticky 只有代码证据，没有浏览器实测」）本身：那条一直挂在「环境」一栏，理由是 in-app 浏览器视口固定 735×900 且不可 resize。

**那条环境判断是错的。** headless Edge + CDP 的 `Emulation.setDeviceMetricsOverride` 可以设任意视口，Node 24 自带 `WebSocket` 不需要装依赖。视口宽度从此不再是「本机碰巧是多少」，而是一个可以扫的参数。

**根因是两半的降级只写了一半。** 带宽 622px 是 `.traj-controls-actions` 那十个中文标签钉出来的，且它**不随视口变**（360→640 全程恒为 574px）。而 `.traj-controls` 是 `flex: none`——整条链的宽度由内容决定，所以 `.filter-row` 的 `flex-wrap` 只能让 **picker** 掉行，对一个**本身比页面还宽、且拒绝收缩的子项**无能为力。

样式表里那句注释写过「Wrapping keeps the band honest at every width — no clipping, no sideways overflow」，`verify-generation-pin.mjs` 也真的断言了 `.filter-row` 有 `flex-wrap: wrap`。**那句话对行成立，对页面是假的。**

**这次的关键不是缺陷，是修法里有一半会骗人。** 我第一版只给 `.traj-controls-actions` 加了 `flex-wrap: wrap`，同时加了一条断言断言这个属性。守卫绿了，变异也能抓到。**但实测 `documentElement.scrollWidth` 一个像素没变。**

原因是规格行为，不是声明写错：**shrink-to-fit 的 flex 容器永远恰好等于它最宽的一行，所以它永远不可能换行**，无论被告知什么。于是「声明了 wrap」和「wrap 生效了」是两件事，而我那条守卫断言的恰好是前者。

**同刻 A/B**（`.probe\wrap-ab.mjs`，运行时注入样式，一个页面一份数据，只变样式）：

| 变体 | 360 时 docW | chips 高 | band 高 | ≥640 时 |
| --- | --- | --- | --- | --- |
| A 现状 | 622 (+262) | 20（1 行） | 219 | — |
| B **只加 wrap** | **622 (+262)，与 A 逐值相同** | 20 | 219 | — |
| C + `.traj-controls{max-width:100%}` | 606 (+246) | 20（仍未换行） | 219 | — |
| **D C + chips `flex:0 1 auto` / `min-width:0`** | **360（溢出归零）** | 64（2–3 行） | 263 | **与 A 逐值相同** |

B 等于 A 是决定性的那条。真正要打破的是**「宽度由内容决定」这个循环**：`.traj-controls` 需要一个来自视口的宽度上限，chips 需要允许收缩并且 `min-width: 0`（flex item 的 `min-width` 默认 `auto`，即内容最小尺寸）。三条属性**任何一条单独存在都不起作用**。

**四问**

1. **归层** — L2 筛选层的呈现规则，纯 CSS，不写任何 `state`。
2. **关联** — 与 `.filter-row` 的 `flex-wrap` 是**同一套两级降级的下半级**（上：picker 掉行；下：chips 换行），与 `.window-bar-actions` 的 `flex-wrap: wrap` 并列。与 `.traj-controls` 的 `flex: none` 从属——那一条**原样保留**，因为它守的是「类型行不压缩，按钮不被压扁」，本条加的是 `max-width`，不是把它改成可收缩。
3. **布局** — 不新增任何节点、容器、sticky 区域，只加两条声明。带高变化由 `syncStickyOffsets()` 实测接住：实测 360 时 `--sticky-band-h` 219→263px、390 时 241px，下游两个偏移跟着走。
4. **口径** — 零个数字改动。

**守卫拆成三条，因为三条互不替代**：wrap（chips 换不换）、`max-width: 100%`（有没有地方换）、`flex-shrink` + `min-width: 0`（换的时候会不会收缩）。**只断言 wrap 就是一条恒真守卫**——它满足、变异能过、页面一个像素不变。第三条里对简写做了解析（`none` → `0`，`0 0 auto` → `0`），否则 `flex: 0 0 auto` 这种写法能绕过它。变异 15 → **20** 条，新增五条覆盖：删 wrap / 写成 nowrap / 删 `max-width` / chips 改回 `flex: none` / 删 `min-width`。

**修后实测（同一扫描）**：360 / 390 / 420 / 480 / 560 / 600 / 640 / 735 / 900 **全部 `ovf = 0`**；chips 宽度随视口走（296 / 326 / 356 / 416 / 496 / 536 / 574）不再钉死；**≥640 时 chips=574、`--sticky-band-h`=181/143/84，与修前逐值相同**——窄屏以外零回归。

> **一条方法论，与 D20 那条同族但方向相反**：D20 是「守卫全绿，断言的是错的东西」；这一条是「守卫全绿、变异能抓、断言的是真属性，而属性没有产生任何效果」。**断言一个属性存在，不等于断言它起作用。** 只有把「声明了 wrap」和「页面变窄了」放进同一个 A/B，才知道哪个是真的——所以本条的全部证据是一次同刻对比，而不是一组绿勾。

#### D22 — 窄屏检视面板三态（2026-10-12 新增功能）

**chli 的原话**：「目前的检视，在窄窗口下，是在最下面，不可见，需要固定到最下方。当滚动到最下方的时候才正常显示。如果是滚动超过了可见区域，则半高显示，然后有一个完全展开的按钮，我们目前有个展开按钮效果，只有检视是三种状态。滚动到最底部的时候，恢复到正常。」

**这不是缺陷，是缺一个能力。** 宽屏下 `.columns` 是两列，检视常驻右列，读者一眼就能看到它；≤767px 塌成单列之后，它是 `main.columns` 的第二个子元素，排在账本后面 —— 读者要滚到文档最末尾才看得到检视。而检视恰恰是「点某条消息看详情」的**结果面板**：读者点完之后，视线要立刻落到那里。「滚到底才看得见」等于让结果出现在读者已经离开的地方。

**做法**：`position: sticky; bottom: 0` + 两个状态类。三个态：

| 态 | 何时 | 面板 | 把手 |
| --- | --- | --- | --- |
| `flow` | 文档流中（顶端、面板尚未进入视野、滚到文档末尾） | 原高，不吸 | 隐 |
| `docked` | 面板底部被钉在视口底部 | `max-height: var(--inspector-dock-h)`（50vh）+ `overflow-y: auto` | 显 |
| `full` | 读者按了把手 | `max-height: var(--inspector-full-h)`，由 JS 实测写入 | 显 |

##### 四问

1. **归层** — L6 检视层的**呈现规则**，写 `state.inspectorDock`（`'flow' | 'docked' | 'full'`），一个三值字段。它**不写任何 L0 字段、不改 L2 筛选、不碰 L4 账本的行数据**。
2. **关联** — 与 `header-toggle` / 窗口条那一类 `.section-toggle` **共用同一个视觉与 aria 词表**（`aria-expanded` + `aria-label` 随态改写），但**不是同类控件**：别的是两态（展开/折叠），检视是三态。差别落在 `aria-label` 上 —— 别的一侧写「折叠 X」，检视写「完全展开检视」/「收起到半高」，因为它没有「折叠」这一侧。与 `syncStickyOffsets()`（D9）是**同一条 sticky 链的下游，不是同一条**：`--inspector-full-h` 读它实测出来的 `--sticky-band-h` / `--sticky-overview-h`，自己不重测。
3. **布局** — **不新增任何 DOM 节点、容器或 sticky 区域**。只做两件事：给既有 `<section class="panel">` 检视面板加 `id="inspector-panel"`，在既有 `.panel-head` 里加一个按钮。CSS 全部落在既有的 `@media (max-width: 767px)` 块内。**为什么不新开一条 sticky 层**：sticky 元素在**自己的包含块**内吸附，`main.columns` 高 936,000px 而面板自然位置在文档末尾 —— 天然行程充足，**不需要 travel padding**（第一版加了 50vh padding，那正是滚到底时面板和 footer 之间空白的来源，已删）。
4. **口径** — **零个既有数字改动**。新增的 `--inspector-full-h` 是新数字，且**只被检视面板一个选择器读**；`--inspector-dock-h` 是 `:root` 里新声明的常量。三处读点全部已加断言：`verify-inspector-dock.mjs` 的「expanded height is measured from the window and the pinned offsets」「expanded height is written in pixels」「half height is a cap on the panel」。

##### 实测（420×844 headless Edge + CDP，点「显示全部」使文档达 937,954px）

| 步骤 | 滚动位置 | 态 | top / bottom | 面板高 | 把手 |
| --- | --- | --- | --- | --- | --- |
| 顶部 | 0 | `flow` | 1350 / 1795 | 445 | 隐 |
| 文档 10% | 93,800 | `docked` | 422 / **844** | 422 | 显 |
| 文档 50% | 469,001 | `docked` | 422 / **844** | 422 | 显 |
| 文档 90% | 844,180 | `docked` | 422 / **844** | 422 | 显 |
| 按把手 | 844,180 | `full` | 397 / **844** | **447** | 显 |
| 再按 | 844,180 | `docked` | 422 / **844** | 422 | 显 |
| 最底部 | 937,954 | `flow` | 323 / 768 | 445 | 隐 |

`bottom == innerHeight == 844` 在三站上逐值成立，所以「固定到最下方」不是某一处碰巧对。**取样按文档比例走，不按面板位置走** —— 面板被钉住时 `rect.top + scrollY` 恒等于 `scrollY + 422`，用它算目标会把每一站都送到文档顶部去。

> **一条要记下来的自我更正**：我第一版探针用 `panel.offsetTop` 定位面板，`pass = true`，而 `panel-below-fold` 那一站的滚动目标算出来是 **0**，和「顶部」那站完全重合 —— 一条退化的断言。**它通过不是因为功能对，是因为它什么都没测。** 和 D21 那条同族。

##### 三条走错了的修法，都留在代码注释里

1. **`rect.bottom >= window.innerHeight`**（松散比较）—— 「已滚过」和「还没滚到」都成立，于是读者还没到面板，面板就先缩成半高，正是 chli 截图里的「它缩在眼前」。**只有「相等且带容差」能把三种位置分开**：`Math.abs(pr.bottom - window.innerHeight) <= 1` 就是全部修法。
2. **加第二参照 `main.columns` 的底边** —— 推理是「`main.columns` 永不 sticky，面板被钉住时它的底边应该严格在视口上方」。**错在面板是 `main.columns` 的子节点**：钉住面板就是把容器的底边一起钉住。合取式在**每一个**状态下都为假，面板**一次都不吸底** —— 和它要修的缺陷正好相反。
3. **`panel.offsetTop + panel.offsetHeight < scrollY`** —— 账本是虚拟滚动的，面板上方的高度是估算值：实测 `offsetTop` 读 **926,767**，真实布局位置约 **934,100**，**差 7,300px**，规则于是按滚动位置触发而不是按面板离开触发。

##### D23 — D22 的吸底断点比单列断点更窄，于是功能在真实窗口里等于不存在（2026-10-12 当日修）

**chli 的反应**：「我没看到检视面板，你说的半高差别很小，从何谈起。」

**两个问题，同一个根：我只在 420px 上量过，而真实窗口不在那一档。**

**一、断点方向错了（功能整体不生效）。** D22 把吸底只做在 `@media (max-width: 767px)`，而 `.columns` 塌成单列是在 **1080px**。于是 **768–1080px 这一档**：面板被埋在账本下面（因为单列了），又没有任何吸底来补偿（因为断点更窄）——**致病因素和补救措施同时缺席**。这比任何单一状态都差，读者看到的就是「这个功能没有」。而这一档恰好就是 in-app 浏览器实际所在宽度。

实测（in-app 浏览器，截图宽 1794）：`#inspector-toggle` 存在但带 `hidden=""`，`aria-label="完全展开检视"` —— 即 `toggle.hidden = !narrow || !docked` 里的 `narrow` 为假，**整个三态逻辑一次都没进**。

修法：三条 CSS 规则从 767px 块里搬出来，进入**属于它自己的** `@media (max-width: 1080px)`；`INSPECTOR_DOCK_QUERY` 同步改成 1080px。判据从「不早于单列」改成**两条分开断言**：`dockCondition >= 单列断点`（覆盖整个被埋没区间）与 `dockCondition <= 单列断点`（不在并排时吸底）—— **两条一起才是「吸底断点必须等于单列断点」**，只写上界正好放过了这次 shipped 的那条。

**二、「半高 vs 完全展开」的差别，取决于内容高度，与视口宽度无关（这一点我上一轮的说法是错的）。**

| 场景 | 面板自然高 | 半高上限 | 实测 docked | 实测 full |
| --- | --- | --- | --- | --- |
| 420×844，未选中记录 | 445px | 50vh = 422px | 422 | 447（差 25px） |
| 900×1000，未选中记录 | 384px | 50vh = **500px** | 386 | **386（差 0）** |

`max-height` 是**上限**，不是高度。上限高于内容时两态**逐像素相同**，第三个态在短内容上根本不存在。上一轮我拿「差 25px」当结论，却没说那是**内容恰好比上限高 23px** 的巧合——而在 900px 那一档上限反而比内容高 116px，差别是 0。**检视内容越长差别越大；空态和短记录没有差别。**

**这条不能靠改数字掩盖。** `--inspector-dock-h` 是上限，改小它只会让「差别存在」这件事在更多情况下成立，但「完全展开」仍然是同一个内容、只是不再被截断 —— 也就是说**三态的区分度完全由内容量决定，而内容量是读者的数据，不是设计能控制的**。这是设计问题，不是 bug，需要 chli 定：

- **保持 50vh 上限** —— 差别只在长记录上出现，空态下把手点了没反应（看起来像坏了）。
- **改成固定像素高度**（例如 260px）—— 永远有差别，但面板再也不会占掉半屏。
- **短内容时不提供第三态**（把手隐藏）—— 语义最诚实，但多一条「什么时候没有第三态」的规则要守卫。

**一条方法论，和 D20/D21/D22 同族但更该早做**：D22 的全部实测都跑在一个**固定宽度**上，而功能的作用域是一个 media query。**「在某个宽度成立」不等于「在它声明的宽度区间内成立」** —— 探针把宽度写死成 420，恰好落在区间内，于是 39 条断言和 36 条变异全绿，而功能在真实窗口里从未触发过。把宽度改成参数、并且**在断点两侧各跑一次**，本该是第一步。守卫现在也从样式表里读断点、并与脚本里的那个数对照，就是为了不让这个数再各自漂移。

#### D24 — 检视：1/4 高、可拖拽调高、无选中时不可见（2026-10-12，chli 直接指定）

**chli 的原话**：「这个检视是半高么？建议中间状态是整个窗口的1/4，然后支持拖放，resize。然后没有选中的时候，应该是不可见的，只有选中记录，才默认1/4显示。」

**先答他的第一个问题：不是半高。** D22/D23 那版的 `docked` 上限是 `50vh`，但在 900×1000 那一档，面板内容只有 384px、而 50vh 是 500px —— **上限比内容还高，所以「半高」等于内容原高**。他看到的和我实测的是同一件事。

1. **归层** — 全部在 L6 检视层的呈现规则，不写 L0、不改 L2、不碰 L4 行数据。新增**一个**字段 `state.inspectorDockH`（拖出来的 px，`null` = 没拖过）。**可见性不新增字段**：判据是既有的 `state.selectedId`，面板可见 ⟺ 有选中。
2. **关联** — 拖拽 grip 与面板头里的 `.section-toggle` **并列不互斥**：一个改高度、一个改档位，都只在 `docked` 存在。取舍写明：**`full` 时拖动即落回 `docked`**，因为「完全展开」的定义是「没有上限」，而读者刚选的高度正是一个上限。与概览刷选拖拽互不干扰（不同元素、各按 `pointerId` 过滤）。
3. **布局** — **新增 1 个 DOM 节点**（面板上边缘的 grip）。**这一条推翻了 D22 那轮我自己设的「不新增任何 DOM 节点」约束** —— 那是上一条功能的约束，拖拽必须有一个可指的握柄，是 chli 本轮明确要求的。不新增容器和 sticky 区域，面板仍在 `main.columns` 里 `position: sticky; bottom: 0`。
4. **口径** — `--inspector-dock-h` 从 `:root` 常量（50vh）变成 **JS 实测写入的 px**：默认 `window.innerHeight / 4`，被拖过则是拖出来的值，两端都夹（不低于 `INSPECTOR_MIN_DOCK_H` = 160，不高于钉住带留下的 `available`）。读点仍只有一个选择器。空态代码**保留不删**（删它会牵动 `renderInspector()` 早退分支和既有守卫），只是不可见时读者看不到。

##### 实测前先说清三条会坏的地方

- **`touch-action: none` 不是装饰**：没有它，触屏上从 grip 起手的纵向拖动会被当成页面滚动，窄屏布局真正是手机的那些设备上这个功能等于没有。
- **拖拽用 `clientY` 不是 `pageY`**：面板是吸底的，页面坐标会把滚动量算进高度。
- **`pointercancel` 必须一起注册**：拖拽以任何其它方式结束（浏览器收走 capture、第二根手指）都会让拖拽对象活着，之后每个 pointermove 都在改一个没人碰的面板。

##### 守卫

`verify-inspector-dock.mjs` 39 → **61** 条断言，`mutate-inspector-dock.py` 36 → **49** 条变异，**49/49 全捕 0 存活**。

**两处「写点闭集」的诚实记录**：dock 态的写点从 3 涨到 **5**（失去选中要落回 flow、拖拽要落回 docked）。守卫没有只改数字了事 —— 它把五个写者**逐个点名**，各自允许写哪个字面量，因为「数目对」和「位置对」是两回事。

**两条变异存活，都是守卫断言写得太宽，补的是断言不是变异**：

1. 「任何指针都能驱动拖拽」那条变异删掉 move 里的 `pointerId` 检查后**仍然绿** —— 因为守卫搜的是整个文件，而同一行在 `up` 处理器里还有一份。改成**只在 move 的函数体内搜**。
2. 「展开高度不再实测」那条变异把 `available` 的算式换成常量后**仍然绿** —— 守卫只查 `--sticky-band-h` / `window.innerHeight` 等四个名字**是否出现**，而它们确实还在。改成**断言那个算式本身**。

> **一条贯穿本轮的方法论**：D22 的实测跑在一个写死的宽度上，D24 的守卫把「名字出现」当成了「被使用」。**两者是同一类错误的两面** —— 前者是「在某个条件下成立」被当成「在任何条件下成立」，后者是「一个名字出现过」被当成「那个名字起了作用」。凡是断言一个标识符是否被使用的规则，都该断言**它参与的那段算式**，而不是它的存在。

#### D25 — 「完全展开」把账本吃干净了（2026-10-12，chli 直接指定）

**chli 的原话**：「然后全高，把轮次的表格给覆盖了，建议表格至少留整个页面高度的1/4。只有正常滚动到最底部，才完全显示检视。当前点展开全部，检视也没有完全显示，也有滚动条。」

**三条，复现于他眼前那个窗口（900 CSS px 宽）：**

| | 修前 | 修后 |
| --- | --- | --- |

| 展开时可见的账本行高度 | **51px** | **301px** |
| 窗口的 1/4 | 250px | 250px |
| 文档最底部（flow） | 无上限 | 无上限，footer 在屏内 924px |

##### 改的是什么

**只有一处算式**，不动 DOM、不动 CSS：`panelMax = max(160, innerHeight - band - overview - ledgerReserve)`，其中 `ledgerReserve = max(140, innerHeight × 0.25)`。

**一条规则、两个用处**：「表格至少留 1/4」同时约束**完全展开的上限**和**拖拽的上限**。只约束其中一个，等于留了另一扇门进同一个缺陷 —— 读者把上边缘拉上去，行照样消失，而且那时没有任何状态发生变化。两个数字各写一份，就是它们漂移的开始。守卫因此断言的是**两者读同一个变量**，而不是「两者都被限制住了」。

##### 四问

1. **归层** — 仍在 L6 呈现规则，**不新增任何字段**，只改一个已存在的测量表达式。
2. **关联** — 与 D9 的 sticky 链仍是**下游**：`ledgerReserve` 用的是 `syncStickyOffsets()` 实测的 band/overview，不是自己重测。
3. **布局** — 零 DOM 改动、零 CSS 改动。
4. **口径** — `--inspector-full-h` 的**含义变了**：从「钉住带以下剩下的全部」变成「剩下的全部**减去表格那一份**」。变量同时改名 `available → panelMax`，因为旧名字在新语义下会说谎。读点仍只有一个选择器；旧断言的表达式跟着改，并保住了它的检测力（见下）。

##### 探针在这一轮暴露的两个自己的错

1. **它在量一个隐藏的面板。** D24 加了「无选中即隐藏」，而探针从来不选记录 —— 于是每一次测量都读到 `rect = 0`、`mode = flow`，**七步全部自信地报告「没有吸底」**。探针报一个它从未进入的状态，比探针失败更糟。已补：先点一行内容最长的记录，再量；并在报告里加一条「选中后面板只有 N px 高，它多半还藏着」。
2. **它从来没滚到底。** `window.scrollTo(0, scrollHeight)` 只滚一次，而虚拟账本让文档在滚动之后继续变长 —— 实测停在 `y=960,517`，而 `maxScroll=961,613`，**差 1,096px**。于是「面板和 footer 之间有 1020px 空档」这个读数**是假的**，footer 根本就在下面 1,096px 处。已改：反复滚到 `maxScroll` 直到 `scrollY` 和 `docH` 都不再变化，并连采两次；连采的第一次才是要记的那个数，不是好看的那个。

> **一条方法论**：这两条是同一族 —— **探针的读数是它自己造成的，不是页面造成的**。一个从不选中记录的探针，和一个只滚一次到底的探针，都在用「条件不成立」冒充「结论成立」。凡是探针要断言「某状态出现」，就必须先断言「我确实把页面放进了那个状态」。

#### D26 — 「窗口的1/4」和「检视的高度」取大还是取小（2026-10-12，chli 直接问）

**chli 的原话**：「对了，窗口的1/4 和 检视的完整高度，取最大还是最小，你来评估。如果窗口高度的1/4 远大于检视的高度，应该以检视高度为准，也就是说检视的高度是兜底值。」

##### 实测（900×1000，同一页取两端）

| | 内容（无上限时的真实高度） | 窗口 1/4 | 吸底实际 | 展开实际 |

##### 为什么渲染已经是 min

因为两个吸底态用的是 **`max-height` 而不是 `height`**。上限渲染出来的是 `min(内容, 上限)`：内容短于 1/4 就按内容高度显示，内容长于 1/4 就按 1/4 显示并内部滚动。**这正是 chli 要的「以检视高度为准」。**

##### 所以改的是守卫，不是行为

风险不在今天的行为，在于**它是个副作用**：哪天有人把 `max-height` 写成 `height`，短面板里就会出现一截空白，而 `height` 在 code review 里看起来完全合理、其余断言一条都不会响 —— 因为**这一支今天无法用测量保护**（最短内容 752px > 250px，测不到）。

于是三条断言守机制：

- 两个吸底态规则**都用 `max-height`**；
- **任何规则都不给面板设 `height` 或 `min-height`**（`min-height` 会把短面板撑出来，症状一样）；
- 基础规则 `#inspector-panel` **刻意不在第一组里** —— 无状态类时面板在文档流里，本就没有上限，而 chli 要求「只有滚到最底部才完全显示」，给基础规则加上限恰好会把这条收回去。

配两条变异：把 `max-height` 改成 `height`、给上限加一个 `min-height`。两条都必须被抓，且**报告的名字要是各自那一条**。

#### D15 自身的一个缺陷：class 跨重建留存，账本塌成 0（2026-10-12 修）

**症状**：滚到最后一条消息 → 点它出检视 → 往上滚一点 → 直接落到页面最上面。

**实测到的现场**（不是推理，是读出来的）：文档最大滚动 **1,223 px**（视口 900），即整篇约 **2,123 px**；而 `#ledger` 的 HTML 有 **140 KB**、窗口条写着「已显示 200 条」。读轮组的内联样式：

```

```

**每一个**轮组都是 `0px`。`content-visibility: auto` 把离屏元素按 `contain-intrinsic-size` 排版，而没有这个尺寸的元素**按空元素排**——于是 0 写上去、组占 0 高、永不回视口、永不重渲染，账本就这么塌着。因为塌了，往上滚一点就顶到头了。

**根因不是顺序，是 class 的寿命。** `is-skipping-offscreen` 加在**账本元素**上，而 `clear(ledger)` 只清它的子节点、**不动它自己的 class**。所以一次建行加上的 class 一直留到下一次建行：第二次之后挂上去的每个轮组**一落地就是被跳过的**，而 `sizeBuiltGroup()` 量到的正是那个 0。

**为什么本条自己的 A/B 没能抓到**：上面那张表是在「显示全部」下量的，159 组、首批 25 组落在文档顶部、读者也在顶部，于是它们**在视口内**，`content-visibility: auto` 不跳过，量到真高度，`sized=159/159`、误差 +0.07% 全都成立。**那组数字是真的，但它是在一个恰好掩盖了这个缺陷的条件下测的。** 跳过的判定是离屏与否，所以这个缺陷只在读者不在首批附近时发作——默认窗口只有 200 条、跨 2–3 个轮组，小于 `LEDGER_BATCH_GROUPS = 25`，**整个账本就是首批**，而读者为了看最后一条消息在底部。

1. **建行开始前把 skipping 关掉** —— `renderLedger()` 里 `ledgerBuildToken += 1;` 之后、`clear(ledger)` 之前 `ledger.classList.remove('is-skipping-offscreen')`。这治的是根因（class 跨重建留存）。
2. **class 加在测量之后** —— 第一批量完再 `add`。这治的是「测量结果取决于读者当时在哪」。

只做 2 只救得了**页面加载后的第一趟建行**，之后每次轮询重建照旧量到 0。**这一点是踩出来的**：先只做了 2，发布后第一趟量到 `7,279 px` 的正常文档高、以为好了，等到第二次轮询重建，轮组又回到 `0px`。

#### D30 — 三处「能失败的检查」其实不能失败（2026-10-13）

这一条不属于前端分层，但它和 D16 / D21 / D27 / D29 是同一个形态，所以记在同一处：**一个检查读的是自己刚刚写下的状态，于是它永远和自己一致。** 共同的病根不是疏忽，是「检查的对象选错了」——比对了自己，而不是外部事实。

**一、`mutate-anomaly.py` 的「还原成功」以自己为基准**

关键三行：读 `original = WATCHED.read_bytes()` → 变异写盘 → `finally` 写回 `original` → 比对 `read_bytes() != original`。**基准就是它自己读进来的那份字节。** 起点脏不脏，这句永远为真。

实测（在文件尾部注入一条注释后运行）：

```
baseline=0EE44615D8D6  tampered=F532928A27EF  differs=True
index.html restored byte-for-byte
OK  (75 mutations, each caught by the guard that owns the defect)
file still contains the tamper after the run: True
```

即：**起点脏时，harness 打印「已还原」、退出 0、报 75/75 全捕，而文件根本没被还原。**

范围要界定准确，不要夸大。从 `CASES` 里真实取一条泄漏注入进去，**shipped harness 当场抓住了**：

```
baseline verify-anomaly.mjs did not pass; refusing to run mutations
FAILED_NAMES  ["the string \"true\" is not a failure either"]
```

「会打破守卫的泄漏」本来就抓得住。我证明的缺口更窄：**最终那句 `restored byte-for-byte` 在「起点脏但不打破任何守卫」时为真**。所以历史经过里能确定的是——某次泄漏让文件变脏，之后每一轮都报「还原正常」，脏文件一直躺着直到被手工发现（`12f26e9` 那次还原提交）。**最初那一次如何触发，仍然未知；不编解释。**

修法不是换基准（基准只能是它自己），是**加一次独立复验**：扫完再跑一遍基线探针，要求仍全绿。跑完后的状态由一个没参与过变异的过程判定，而不是由写盘的那一方宣布。

**二、`--check` 这个命令从来不存在**

`make-fixtures.mjs` 对任何输入都打印 `(dry run -- pass --record to write)` 然后 `exit 0`，而 `--check` 压根不是它认识的选项。`AGENTS.md` 却把 `node tests/make-fixtures.mjs --check` 列成一条「输出必须保持绿」的验证命令。

期间真实发生的事：已提交的 fixture 与 workspace 副本在 **8 个文件里有 6 个内容不同**（`message_id` 前缀分别 `00ba` / `00bu` / `00cc`）。**没有任何信号。**

**定案：不比字节，比形状。** 承诺从来不是「与本机今天蒸馏出的结果逐字节相同」——活存储一直在动，逐字节比在本机会**永久红**（连续两次取样，同一条会话的行数几分钟内从 63 变成 81；`--record` 会改写 8 个文件里的 7 个）。真正承诺过的是那个更弱、也更持久的三条：fixture 仍按服务读它的方式解析、仍覆盖 `verify-anomaly.mjs` 断言的**全部十种 shape**、仍不含本机信息。加第四条：**再蒸馏一次必须读出同一个结果**（`classify(synth(row))` 与 `classify(row)` 的 flags 必须一致）——空字符串负载经 `synth` 会变成占位文本，于是不再「空」，`silent` 那条规则就悄悄失效了。

`--check` 插在 `resolveSessionsRoot()` **之前**，因此它**不读活存储**，在没有任何 `~/.minimax` 的 CI 上也能跑。实测：**8 sessions / 385 rows / 十种 shape 全覆盖 / OK**。并在真 fixture 上注入一个机器路径验证它会红：`FIXTURE CHECK FAILED (2)`，并点名 `fixture leak /[A-Za-z]:[\\/]/ in ...messages.jsonl`。

**三、函数判对了，分支看不见 —— 第一版守卫的变异存活了**

这一条最值得记。写完 `--check` 之后我给它配了自检：`--checkselftest` 造一好三坏，要求每种坏都被按原因拒绝。**然后做变异，把打印结论的那个分支废掉：**

```js
if (r.problems.length) {  →  if (false && r.problems.length) {
```

**守卫全绿。** 因为 `--checkselftest` 是在进程内直接调 `checkFixture()`，而函数判得完全正确；被废掉的只是「把判定变成退出码」这一步。于是 `node tests/make-fixtures.mjs --check` 照样打印 `fixture check OK`、照样退出 0。

> **一个性质可以被算得完全正确，同时对别人真正会走的每一条路径都不可见。**

修法是给 `--check` 加 `--root=<dir>` 和 `--emit-demo-tree=<case>`，让守卫**驱动真正的 CLI 分支、读真正的退出码**，而不是在进程内调函数。补完之后同一条变异立刻被按名捕获（3 条断言红）。

补守卫的过程里又撞出两个同源的洞：

- `--check` 打印的 `fixture root` 改成常量，守卫照样全绿——**没有任何断言说它报告的是自己判过的那棵树**。补：断言输出里出现传入的 root，且不含已提交 fixture 的路径。
- `if (!passed) ok = false` 废掉，守卫照样全绿——因为健康树上四个 case 本来就全过，`ok` 永远不会被置 false，**「漏了一个 case → 进程退出非零」这条接线在正常运行下根本无法被观测**。补：`--checkselftest-broken` 塞一个必然失败的 case，强制走失败路径。

**结论（写进 `tests/METHODOLOGY.md` 的判据）**

1. 能失败的检查必须**相对于外部事实**，不能相对于自己读进来的状态。
2. 它还必须走**别人真正会走的那条路径**。函数正确不等于分支正确。
3. 常量也要能被打破。`SESSIONS_FLOOR` / `ROWS_FLOOR` 原本只是数字，各补了一个 demo tree 才变成不变量。

守卫：`tests/verify-fixture.mjs`（18 断言）+ `tests/mutate-fixture.py`（10 条变异，**10/10 全捕 0 存活**）。全套 **53/53**（原 51）。

**四、顺带：`.gitattributes` 与一个被行尾暴露的老 bug**

插件目录新增 `.gitattributes`（`* text=auto eol=lf` + `*.png binary`）。放插件目录而不是仓库根——放根会改所有插件的行尾，而这是单插件 PR。所有 blob 本来就是 LF，**零 blob 变动**，只是工作区不再与提交不一致；`server.mjs` 顺势从 CRLF 归一回 LF（108,982 → 106,493 字节，两棵树同步转换，blob 哈希不变）。D18 那条「不要对 `index.html` 用 `git stash` / `git checkout`」的禁令据此解除。

它当场暴露了 `mutate-host-only.py`：`L = "\r\n"` 硬编码，四个锚点全部停止命中。其余 harness（`mutate-steer` / `compaction-turn` / `parsed-rows` / `pr15-fixes` / `raw-lazy`）早就在**从文件自身读行尾**，它唯一的例外。修法对齐既有约定：**任何锚点都不含换行**，必须插入时的那一个换行从待编辑文件里量出来。

## 3. 分层模型

| 层 | 名称 | 拥有 | 回答 | 读 |
| --- | --- | --- | --- | --- |
| **L0** | 数据 | `server.mjs` 的 payload | 会话目录里有什么 | — |
| **L1** | 上下文 | 会话、上下文代、跟随最新、刷新 | **看哪段数据** | L0 |
| **L2** | 筛选 | 类型、异常规则、搜索、时间区间 | **看哪些记录** | L1 |
| **L3** | 投影 | 总览条、轴模式（等宽/真实）、窗口分页 | 同一批记录怎么画、画多少 | L2 |
| **L4** | 汇总 | KPI 卡 | 这段时间的整场会话 | L2 的**区间一个字段** |
| **L5** | 列表 | 账本行、轮头 | 逐条记录 | L2 + L3 |
| **L6** | 检视 | 单条记录的四视图 | 这一条长什么样 | L5 选中的 id |

流向单向：`L6 ← L5 ← L3 ← L2 ← L1`，`L0` 在最底下。**唯一允许的向上写**是 L3 → L2 的区间刷选（见 R5）。

### 五条不可违反的规则

- **R1 一个字段一个写者。** 每个 `state.*` 只允许一个 setter 函数写入。互斥关系必须在这一处表达，不能散在两个渲染函数里。
- **R2 可见性只有一个入口。** 「这条记录在不在屏上」只有一个函数回答；L3 的 span、L5 的行、L4 的口径全部走它。现在 `visibleEntries()` 和 `spanPassesFilter()` 是两个入口，这是 D 类缺陷的结构来源。
- **R3 L4 只读 L2 的区间字段，其余不读。** KPI 不是筛选的函数，它不因类型轴变化而变化。
- **R4 L6 不回查。** 检视只接受 L5 交付的选中记录 id。
- **R5 L3 → L2 只有区间一条回写，且必须走同一个 setter。** 总览条不允许自己维护第二份区间。
- **R6 控件位置与它写入的层可以不同，但必须声明。** 本页已知的两处：`window-bar` 在 L5 面板内、写 L3；`overview` 是 L3 的投影，同时持有写 L2 的控件。

## 4. 加功能之前：四个问题

**顺序是硬的**：这四个问题的答案写下来（进 PR 描述或本文件的增量）之后才允许写实现代码。答不上第一个，说明这个功能不属于这个页面，或者需要先改模型。

1. **归层** —— 它改的是哪一层的状态？
   改不了层归属的，不做。
2. **关联** —— 它和**同层**已有控件是并列、互斥还是从属？
   互斥必须表达在同一个地方（R1）。不能靠「B 改的时候顺便把 A 清掉」这种跨函数约定。
3. **布局** —— 它的容器是哪个已有层容器？需要新的 sticky、panel 或层吗？和邻居的视觉语言一致吗？
4. **口径** —— 它是否改变任何已有层**对外承诺的数字**？
   若改变，列出所有读那个数字的地方（按钮、提示、KPI、span、轮头），逐个加断言。这一问是「联动异常」的主要来源：加了一个能力，改了一个数字，别的地方还在按旧口径说话。

### 反模式清单（每条都从本页的代价里长出来）

- ❌ 把新控件放进「离它作用对象最近的地方」，而不是「离它所属的层最近的地方」。
- ❌ 用「加一套第二系统」的方式扩展，而不是给现有系统加一个字段（异常轴本可以是 `anomaly: {mode, rules}` 一个字段）。
- ❌ 让新控件自己解释全局状态（合计、是否已是默认、按下态），而不是读同一份快照。
- ❌ 把只读汇总放在操作区上方，让读者以为它随操作变化。
- ❌ 在没有共享层的前提下，用散落的互斥分支维持不变量。
- ❌ 先实现、再补布局、再补守卫。**这条的顺序反过来才对**：归层 → 关联 → 布局 → 口径 → 不变量 → 实现 → 守卫。

## 5. 分阶段迁移

每阶段一个独立改动、独立守卫、独立浏览器实测，不合并。

### Stage 0 — 谁负责重算（D8 / D9，**已完成**）

先修「位置与位置变了之后由谁负责重算」，再谈其它。这一步已经落地：

三条共用同一个出口，是因为它们回答的是同一个问题：**这次重画，哪些状态要重新判定。**

### Stage 2 — 把异常轴变成 L2 的字段（模型）**2-a、2-b 已完成；2-c 的注释半完成，赋值半显式不做**

四项任务：收字段、合成 R2 单一入口、`resetBaseFilters()` 变成一次赋值、删掉 D2 那句注释。读点已经数清，四问如下。

**归层** L2。三个字段今天就已经住在 `state` 里（L2 那一组），本条不改变它们属于哪一层，只改变**它们是不是一个东西**。不改 L1/L3/L4/L5/L6 任何一层，也不动任何 DOM 位置。

三处判断，逐条对着代码：

1. **笔刷为什么是参数而不是 state 读。** 原来两个入口对笔刷的处理就不一样：账本经 `passesBaseFilter(record, selection)` 用笔刷，总览条不用。总览条**必须**不用——笔刷是画在它上面的，一个把自己正在被拖选的记录藏起来的条，没法用来拖选。把它写进签名而不是留给读者猜，是为了让下一个人不会「顺手修正」总览条。断言守的就是这个：`recordVisible` 的函数体里不得出现 `state.overviewSelection`。
2. **`turn` 为什么是参数。** `flattenTurns()` 产出 `{turn, record}`，账本拿得到；条只拿到裸 record，所以要从 `turnById` 查回来。两者拿到的本来就是同一个对象。断言守的是账本**不自己查**（`visibleEntries` 不得出现 `turnById`）——它手上已经有那个对象了，再查一次是同一个对象换个来源，将来两边会长歪。
3. **互斥由 `return` 表达，不由 `else` 表达。** 「两个轴是二选一不是叠加」这条断言原来只读 `if (anomalyMode) … } else if (!passesBaseFilter`，它守的是 `else` 的存在。新的断言要求异常分支 `return`，且基础判断写在它之后——一个只判不回落的分支就是叠加，只是拼法相反。

| 断言 | 守的是 | 变异 |

#### 协议

请求：`GET /api/trajectory?session=…&generation=…&since=<游标>`。游标是可选的**整数 ≥ 0**；缺失、空、非整数、负数都**不是错误**，一律当作没有游标，返回整包——一个什么都还没有的页面需要的就是整包，把首轮轮询变成 400 是比发 41 MB 更差的答案。

响应多一个顶层键 `delta`：**有 `delta` 就合并，没有就整体替换**。这个标记是判定的唯一依据，客户端因此不需要猜服务端这次发的是哪种。

```jsonc
{ "session": { /* 整包 */ },
  "stats":  { /* 整包 */ },
  "turns":  [ /* 只有新增记录的轮，且整轮携带 */ ],
  "delta":  { "since": 21584, "upTo": 21642, "records": 8 } }
```

三个设计判断，逐条对着代码：

1. **`stats` 整包来，因为它是个累加器。** 里面每个计数都是遍历全部行累加出来的，尾部无法被「加」到它上面——要那样就得由客户端重新推导服务端自己的算术。`session` 同理：几百字节，而用上一份回答它会让每个 payload 依赖一份服务端并不保留的历史。
2. **轮整轮携带，只切 `records`。** 这重复了页面已有的字段，是刻意的：一轮对话进行中 `closed` 会翻转，而 `无答复` 就是由它判定的。发一个残缺的轮，页面就会对**唯一那个还在被写入的轮**持有过期的 `closed`——恰好是决定这些行算不算异常的那一轮。
3. **游标超过末尾时返回 `null`，即整包。** 那是**页面跑到服务端前面**的样子，也就是从服务端看「切了一代」。从那儿切出的尾部是空的，而空尾部与「没有新东西」不可区分。

#### 服务端：只在冷构建路径上切

缓存命中那条路径**不处理 `?since=`，且这不是遗漏**：带游标的页面一定也带着它对应的校验器，所以带着游标走到这一行意味着会话变了——那正是下面那条分支。而从缓存 payload 里切尾部还要求把那个 payload 留在内存里，这个缓存刻意不留：它留的是序列化后的字节，和 `/raw` 需要的 rows，不是字节背后的对象图。

**所以 `?since=` 省的是传输与客户端 `JSON.parse`，不是服务端 CPU**——服务端仍然全量读、全量解析、全量构造、全量 stringify（缓存条目和 `/raw` 都需要整包 body）。实测证实了这一点，见下。

#### 客户端：游标与校验器同一个条件

`state.since` / `state.sinceFor`，用法与 `etag` / `etagFor` 同构：**游标只在与校验器同一个条件下发出，且按同样的方式绑定 cache key**。手动刷新同时丢掉两者——它是在向服务端要真相，尾部不是真相。

`applyPayload` 的合并以 `body.delta && state.payload` 为前提，缺一不可：只认标记会在会话切换后把一个会话的尾部合到另一个会话的轮上去。

`mergeTurnRecords` 按 `record.index` 取并集而不是追加，所以**同一个尾部被重放两次什么也不会变**——重试和重叠轮询都会发生，只在顺利路径上正确的协议会在第一次重放时丢记录。轮级字段取自来件，所以 `closed` 会跟着翻过来。

#### 实测（本机，服务端 55344）

冷缓存、同一会话、同一轮询：

| | 字节 | 服务端墙钟 |
| --- | --- | --- |
| 整包 | **43,159,724** | 1,124 ms |
| `?since=21584` | **19,663**（**0.046%**） | 1,124 ms |

delta 标记 `{"since":21634,"upTo":21642,"records":8}`，1 轮 8 条，索引 21635–21642。**服务端墙钟两次相同**——这就是「省传输不省 CPU」的直接证据，不是推算。

浏览器端（重载后正常轮询约 6 分钟）：

- 窗口条「共 21,680 条」，同一时刻 API 报 21,679 条，**差 1 条正是两次读取之间我自己产生的记录**——两个来源同步，合并没有丢也没有重。
- console 零 error / 零 warn。
- 网络面板：无变化轮 304、约 30 ms；会话增长轮 200、约 640–710 ms。**200 轮仍是 650 ms 量级**，因为服务端那部分没变——这正是预期。

#### 证据边界（不要读过头）

网络面板**不返回响应体大小，也不返回 URL query**。所以「那些 200 是尾部而不是整包」这一点，**不是**从面板读出来的；它是冷缓存直连测出来的（上面那张表），面板只能证明轮询节奏与状态码正常。把面板的 `durationMs` 当成「省了多少」的证据是读过头。

另外 304 在面板里显示为 `outcome: failed` + `net::ERR_ABORTED`：304 没有正文，页面在读正文之前就 `return` 了，浏览器因此把正文流标为中止。这条 304 处理路径本轮**一行未改**，我也没有做改动前的 A/B 对照——**按推理它早于本改动存在，但没有实测证据**。
