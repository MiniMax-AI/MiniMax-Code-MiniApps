## 逐轮的缺陷与修法

- 版式与字号本轮整体上调了两档，随后在 1524×1304 视口下逐页目视核对：起卦、解读（卦体行、
  四卦推导、卦气消长环、八宫名单）、卦库、历法（十二时辰、二十四节气、十二生肖）、卦历
  （存了一条 40 字长问题的条目），均无折行与溢出，浏览器控制台无报错。
- 卦画的可读性立了两条断言，这两条都曾经是真的、远看只是一团灰：阴爻不许再用
  `--border-strong`（只两成黑，当初是为了让阴爻「退后」），爻画也不许退回 4–5px 的发丝粗。
  阴阳本来靠形状分——一整条对断成两截——明暗再掺一脚只会把卦画弄糊；解读页那副主卦体
  的粗细下限也比旁边的小卦图更高。
- 十二时辰的网格立了常驻断言：列数必须整除 12，时间与神煞两行不许折行。这条曾经真发生过——
  `auto-fit` 轨道会悄悄把格子挤窄，`03:00 - 05:00` 折成两行，同一排卡片便高矮不齐。
- 另有三处版式缺陷立了断言，都是实机看出来的、不是推演出来的。八宫名单那一行顶对齐，
  唯独本卦那一格为了朱砂框带了 border 与内边距，于是只有它被顶下去 5px，看着像「掉下去」；
  框改成 outline，画得出来又不占位置。消长环的爻杠伸得比标签挂得还远，那两个满六爻的格子
  （乾巳、坤亥）爻杠正压在「乾」「坤」的字上；标签退到 R+40，画布同时从 200 扩到 232 见方
  才腾得出位置。环的呼吸动画原先把当月格压到 0.55 透明度，等于每 2.6 秒把它指的爻杠闪到
  看不清一次，现在最低只到 0.8。
- 解读页两栏原本右栏远长于左栏，滑下去左侧便空出一大片。现把标题与四个分区合成一条钉住的
  顶栏（半透明底加模糊、下缘一道分隔线），左栏在宽屏且视口够高时钉住并按顶栏高度错开。
  顶栏高度原先写死在 `:root`，实测发现那是 1340px 宽下的值：把内容区收窄到 700px，顶栏里
  标题、副题与干支条排不下就分两行，顶栏长到 195px 上下，左栏仍按 132px 错开，「天风姤」
  卦名直接被压在顶栏底下。高度改由 `ResizeObserver` 实测写回，`--topbar-h` 只作首屏兜底，
  `:root` 里那个值不再是两个地方各写各的数。
- 四卦推导与八宫名单改成按自己这块有多宽排版，不按视口。两块原先都是 flex 换行：内容区一收窄，
  推导那四格折成 3+1、八格折成 7+1，末格孤零零居中，像是掉了出去。现在各自是一个具名容器
  （`container-type: inline-size`），列数由 `@container` 定——推导四列或两列，八宫八列或四列，
  列数一律整除总数，不留落单的一行。两块都在右栏里，右栏多宽由左栏与版心决定，跟视口不是一回事；
  拿视口宽度定列数，就会出现宽屏配窄右栏、排得参差的情形。有一条断言反向钉住：任何 `@media`
  规则都不许碰这两块，列数才不会又漂回视口上。
- 推导图里箭头与卦裹成一格，不再是平级的两项。互卦那条注记两行、其余各一行，箭头原先是垂直居中
  的 flex 列，于是它比另外三支低半行，四支不在一条线上。现在注记是上下居中的 flex 盒子、定高两行，
  本卦那一格横跨整行居中而不是落在第 1 列；断行由数据里的 `\n` 决定（`white-space: pre-line`），
  不看 `max-width` 恰好折到哪儿。那个宽度原先是 88px，而最长的注记分段是七个汉字，按注记 13px
  算要 91px——于是互卦那条被折成三行，箭头又离了线。断言逐段量一遍：盒子窄过字要占的宽度就报红。
- 版心内边距收成一个值。`.app` 原先左右各写死 32px，在 1149px 视口上白白吃掉 64px 宽度，推导图与
  八宫正是被这一点挤到换行的。现在是 `--app-pad: clamp(14px, 2.1vw, 32px)`：`.app` 用它，`.topbar`
  用它的相反数——两处各写一个数，内边距一收放顶栏底色就不贴视口边。顶栏的外边距与内边距、解读页
  两栏之间的缝、左栏的宽度，都断言跟着这一个值走。
- 左栏一度被收窄到 `clamp(232px, 21vw, 366px)` 想给右栏腾地方，那是错的。爻行那一格是
  `34px + 42px + 1fr + 32px + auto` 再加四道 12px 的缝，固定部分先吃掉 156px，留给纳甲（干支、六亲、
  世应、旬空月破，全是 nowrap）的那格还得有 140px 出头。窄过 300px，纳甲就撑破格子探到右栏去，
  爻画同时被压没——阴阳一眼就读不出来了。现在是 `clamp(300px, 26vw, 366px)`，下限照着爻行真正
  需要的宽度钉死。`minmax(clamp(...), 366px)` 先试过，是空转：上限是死数，内容只要够宽轨道就一直
  顶在 366px，下限永远轮不到。
- 本轮新增的六项断言都做了变异验证：两条容器查询、四处列数、格子包裹、注记盒子、版心单一来源、
  左栏下限，以及「视口查询不许碰这两块」那条反向断言——逐个把实现改坏，确认对应断言真的报红，
  27 条全部钉住，脚本跑完还原后 212 项全过。写脚本时又踩了两个坑，其中一个是真把测试写松了。
  脚本原先拿每条变异的预期断言去比**用例标题**，而预期写的是断言消息，于是一轮全部正确的运行
  报出 26 条没钉住；现在改成读失败详情。窄屏那条断言写的是 `grid-template-columns: 1fr`，
  `1fr 1fr` 照样匹配——测试实际在替两栏那条作证，却声称钉的是单列；补上收尾分号才分得开。
  只在 `finally` 里还原是第三个坑，上面那条已经记过：第 N 条变异会跑在第 1 条改坏的文件上，
  看着像「测试没钉住」，实为污染。这一轮的每条变异动手前都先从干净基线还原。
- 通盘审下来又挑出三处缺陷，都在卦历落盘与起卦 id 上，现已修掉并各自钉住。原先的 id 是秒级
  时间戳加卦序、动爻一起哈希。数字起卦只取决于那两个数，所以同一秒内起两次同样的数会得到
  分毫不差的同一个 id——而起卦按钮在整个推演动画（要停 `CASTING_HOLD_MS` 那么多）里一直可点，
  普通双击就真的会发出两次请求。两条都存进卦历，之后 `remove(id)` 按 id 过滤，删一条连带把另一条
  也删了：实测存入两条同 id 记录、删一次、剩零条。现在 id 的种子掺了一个进程内单调递增的计数，
  断言钉的是后果而不是某个字面串——同一秒内同一卦的两次起卦 id 必须不同，删一条必须留下另一条。
- Windows 上把文件改名覆盖到已存在的目标，若目标正被别的进程以未共享删除权限的方式打开
  （杀毒扫描、搜索索引都算），会整个失败并报 `EPERM` 或 `EACCES`——不是半截写入，是压根没换，
  这次保存就这么丢了。现在遇到 `EPERM`/`EACCES`/`EBUSY` 退避重试至多四次（累计约 400ms），
