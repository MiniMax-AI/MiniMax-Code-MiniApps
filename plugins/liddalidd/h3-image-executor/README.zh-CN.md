# H3-Image-Executor（`h3-image-executor`）

[English](README.md)

一个把一句话需求跑成经过校验的 4K 图片的 Mini App。你描述画面，它负责检索参考图、规划分镜、
生成、看图评审、色偏校正、有限次修正、选优，最后交付图片和一份验收报告。

![一次四张图任务完成后的面板：需求、折叠的过程详情，以及带预览、分享和公开链接按钮的交付图](docs/dashboard.jpg)

它围绕 **H3-Image** 生成接口构建。该接口不属于 MiniMax 开放平台的公开图片接口，因此在使用前
你需要自备 H3-Image 的接口地址和 Key，详见[配置接口](#配置接口)。

## 它做什么

- **先规划再动笔。** 规划节点把一句话拆成分镜：每张图一份规格，各自的画幅、硬约束和偏好。
- **自己找参考图。** 要不要检索、搜几项、肯花多少次，由规划按这次需求自己判断，不是每次都搜。需求里出现专有名词或
  特定称谓（真人、角色、品牌和产品、logo、车型、地标、具体的作品，或者不确定长什么样的冷门叫法）时，规划会先去检索；
  通用的东西、常见的画风和版面类型，有把握画对就不搜，觉得参考一张真实样例能明显更准时再搜。规划同时给一个检索预算
  （搜图一次、判定一批候选各算 1 次，最多 16 次，没写时按每项 2 次、至少 8 次），按检索项的顺序花，每搜一项都给它留一次判定，
  别的项换说法重搜、多判几批都不会占用这一次；候选一张都没下载下来那一批没调用判定，不算次数。花完就停，没搜或没判完的项在交付说明里照实写「超出检索预算」，不说成没找到。每张参考图都记着用途（主体外观、局部、画风、
  版式、场景）和要取它什么，生图时逐张告诉模型，免得把某一张当底图照搬；底图要留白给程序排字、画图表的图，
  版式参考图（上面全是字）不送进生图。判定先看候选是不是这个东西本身；角色和吉祥物的官方插画、雕像或手办照片都算；
  画风、版式、场景参考只要是这一类的真实样例就能用。一整批都被否掉时，
  它会换一种说法（比如主体在原产地语言里的名字）重新搜，而不是在同一批结果里往下翻；第一次检索搜图服务就报错、
  或者一张都没回的，也用规划给的另一种说法再搜一次（工具被拒的不再试）。
  点名一部真实存在的作品（电影、剧集、动画、游戏）当主题时，会检索它的官方海报或剧照，参考主角的经典造型、
  标志性道具、配色和片名字体；人物的脸照原创画，你点名要像某位演员时除外。
- **多图锁定角色外观。** 多图任务会先生成一张角色设定图，并把它绑到每一张图上作为参考，
  避免同一个主体画到一半变成另一只。
- **看图评审。** 每张候选都由视觉模型按约束逐条核对，而且评审看不到送进模型的那段 prompt，
  不会被 prompt 说服。
- **工具调用次数按难度给。** 规划、评审、修正、选优、追问编辑这些节点每次能调用几次工具，不再写死，而是每次调用前现算：
  这一步必须打开的图（每个候选的看图材料、参考图材料……）加 1 次余量，再按这张图的难度加（规划判简单、一般、难，
  分别加 1、2、4 次；没判就按规格推断，比如 8 段以上的文字、要对照两张以上参考图、8 帧以上的动图算难）。
  某个节点在这张图上撞过上限，下一次再多给 2 次；每个节点另有封顶。提示词里写的上限和运行时执行的是同一个数，
  时间线的节点详情里写明这个数是怎么算出来的。
- **量色偏。** 偏红由程序实测判定而不是靠眼睛看，判偏红的图会重画而不是直接交付。红的是主体本身（橘猫、红围巾、
  暖光下的产品）、而画面里接近中性的地方颜色是正的，不算偏红。需求要的主色本来就是黄、红、橙（明黄底的海报），
  画面里又几乎没有中性色时，程序判不了白平衡，不算偏红，交给评审看；这类图的 prompt 也不再要求「不要偏暖发黄」。
  需求写明白色纸张、白底时，程序单独量白色的地方：红绿蓝相差 4 级以上（发紫、发粉、发黄、发蓝）就判不通过、重画，
  整图均值看不出这种偏色。
- **多轮编辑不越改越偏。** 每张图记下第一张颜色合格的候选当色彩基准。之后每次在别的候选上编辑（修正轮、追问），
  都把它当第 2 张图一起送进去，说明只用来对照色调、白平衡和纸面白度。追问里明确要改颜色、光线时这一次不带，
  改完以后重新选。
- **放能扫的二维码。** 生图模型画不出能扫的二维码，它画的只是长得像码的黑白方块。需求里要码时，
  规划节点把码里放的内容从你的原话里逐字抄下；每张候选出图后，程序找到模型画的码，换成跟随原来透视和明暗的
  真码，再从最终文件扫码验证。扫不出就和别的硬约束一样判不通过、打回重画。要码却没说放什么，会照常出图，
  交付时注明是装饰码；你在同一会话里补一句内容，程序直接在交付图上换成真码，不重新生图。
- **大段文字由程序排版。** 生图模型写不好长段文字、竖排和毛笔书法：一次真实任务要的是 324 字的《兰亭集序》全文长卷，
  第一轮的候选有编出来的字，交付的那张漏了 36 个字（含一整句），追问补字后又跑了 4 轮仍没过检查；评审也没法逐字核对
  这么多字。遇到这类文字，应用让模型只画一张把载体留空的图（纸面、招牌、海报底板），再由程序用字体把文字逐字排上去，
  跟着载体原来的明暗和纹理走。一段 24 字以上（或合计 40 字以上）、竖排 10 字以上、毛笔字 12 字以上的文字第一轮就走
  这条路；短标题先让模型直接画，评审判出每张候选的字都写错了、且规划写明了标题的位置时再切过来。预留的地方其实没留空，
  就打回重画。之后改字（内容、字体、大小、颜色、标点）直接在保存下来的无字底图上重排，几秒钟就好，不调用生图接口。
  排课本、书刊这类版面时按排版规矩来：同一角色的文字（几段正文、几条标签）统一成同一个字号，脚注、页码不比正文大；
  正文首行空两格、两端对齐；正文和标题里的脚注符号（①②…）排成右上角的小字，脚注区每条开头的序号保持正常大小；
  脚注上方画一条短分隔线。一张图最多排 16 段文字，超出的段落如实列在交付说明里。
  每段字只在自己的规划位置附近找空白：规划位置被模型画的线、色块压住时，就近上下挪开（最多两个框高）；
  别的段的规划位置和已经排好的字都算占用，两段字不会排到一起，程序最后还会逐字查一遍，叠了就不交付。
  段落多时，给模型的留白要求按整片区域描述，不逐段写坐标（逐段写的百分数会被模型画成一页数字）。
  评审判出字的位置不对（压线、出界、该在色块里却在外面）而底图本身没问题时，只在同一张底图上按新位置重新排字，
  不调生图接口，也不占重画的轮次，每张图最多两次。
  一个字里要两种颜色时（识字挂图：「清」的「氵」橙色、「青」深灰），字照样作为完整的一个字排，程序在字形上找偏旁和
  其余部分之间墨最少的一条切线，切线靠偏旁那一侧上另一种颜色；偏旁在左、右、上、下都行。字体里部件连笔切不干净时
  （毛笔字常这样），这一层自动换宋体或黑体；都切不开就整字一种颜色，交付说明里照实写。标题、标签、示例词这类短文字
  默认排一行，排一行字号小得太多才换行。规划完程序先把文字层按位置从上到下、从左到右读一遍，和你原话引号里的文字对照，
  读不出来（比如把「清」拆成了「氵」「青」两块）就把具体问题交回规划改一次，改过还是对不上，评审会按图核对，交付说明也会写明。
  规划提示词里写明了本机各书体实际用的字体：没有楷体字体的机器上（macOS 默认没有），「楷体」用的是毛笔楷书。
- **用一张参考图做 GIF 动图。** 生图模型一次只出一张静态图，动图按 4–16 个关键帧来规划，帧数按动作幅度定：眨眼、挑眉
  这类小动作 4–6 帧，转头、手从画面外抬进来这类大动作 10–16 帧，相邻两帧只差一小步。第一帧从参考图改，
  后面每一帧在前一帧上接着改一小步，同时把参考图一起送进去，锁住身份、服装、背景和颜色：每一帧单独从参考图改的话，
  模型对同一句「双手抬到胸口」每次画得都不一样，手一会儿高一会儿低。最后由程序拼成循环播放的 GIF。
  模型每改一帧都会把整幅画的细纹理重画一遍，画面还会错开一两个像素，所以合成时程序先把每一帧对齐参考图、校正色调，
  只留下真正在动的部位，其余一律用参考图的像素，背景不会闪；相邻两帧之间默认补两帧渐变，首尾是同一张图时并成一帧，
  循环接缝处不会卡一下。你给了图，就直接照这张图出帧；没给，先画一张参考图交给你确认或修改，点「生成 GIF」之后才出帧，
  1 分钟内没有回应就按默认确认、自动开始出帧。
  一次评审对照参考图看全部帧，只重画判了不合格的帧，最多一次。回到前面某个姿态的帧直接用那一帧的图。
  帧画完之后，程序把每一帧锁回参考图、量相邻两帧变了多少：一步变了超过画面的 9% 的地方补 1 帧过渡，把前一帧和
  后一帧都送进去，以前一帧为底画两者正中间的状态，评审照常核对，没过评审的不用，来回往复的动作只画一次。
  每一帧停一样久，整组时长按规划的关键帧数算，补了帧也不会忽快忽慢。重画一次还没过评审的帧不放进 GIF（交付说明里写明），
  免得动作往反方向走一下；它留下的空当照样按前后两帧补一帧过渡（不管量出来变了多少），提示词里写上它原来的计划，
  补上的就顶替它的位置。补不上时它的那一份时间留给前一帧，动作照计划的速度走，不会一帧跳一步、一帧跳三步。
  评审也会核对参考图里有的文字、符号、道具每一帧都在。渐变只补在差得不多的两帧之间：
  差得多的两帧叠在一起是两个半透明的人影，看起来是闪而不是动。GIF 写出去之后再读回来，核对帧数、尺寸、每帧时长和是否循环。
- **分格组图切开拼成 GIF。** 一张图里排好的几格（六格表情、四格漫画、九宫格）是模型一次画出来的，同一个角色、同一套画风，
  比一帧一帧分开画一致得多。交付之后说「把这组图变成 GIF」，程序找出格子之间的分隔线或留白，把每一格切开、修掉分隔线，
  统一成同样大小，再按画面对齐（模型在每一格里画的主体位置差一点，原样播主体会一跳一跳的），从上到下、从左到右拼成循环的 GIF。
  组图本身不重画。相邻两格之间会各补一格中间状态（过渡格），动作一步一步地走，不是一下子换掉：过渡格一起生成，
  先由 Agent 看着组图写每一格要改成什么样（手抬到哪、嘴张多大），再在原组图上改一次，一次出 2 张候选；每一步先由程序筛掉照抄了
  前后格的，再由评审从剩下的候选里挑一格，没挑到的步子再出一轮（最多两轮）。只说「画两格中间的样子」的话，模型几乎都是照抄下一格。
  过渡格对齐到它所在那一格的人物上（平移和缩放），背景用那一格的像素，只留下真正在动的部位，背景不会闪。
  要多一次生图，约 1 分钟，加上两次 Agent 轮次。默认每格停 0.7 秒，第一格 1.05 秒、最后一格 1.4 秒，过渡格 0.18 秒（从前一格的时间里扣）。
  格与格之间换了场景（讲故事的四格漫画）不补；你说「不要补帧」也不补。所有帧共用一套调色板，写完从文件读回来核对。
  需求里一开始就说要组图再做成 GIF，规划会直接这么安排，组图评审通过后补好过渡格一起交付。
- **绕中心转的动画由程序转出来。** 加载圈、转圈的图标、齿轮、风车、唱片这类动作，让模型一帧一帧改画不准：十二个点的加载圈，
  十二帧里有一半亮点落错了格子。这类需求规划只让模型画一张图，评审通过后由程序按圆心把那一块圆盘转出各帧：一格一格跳的
  （圆环上等距的点）每帧转一格，暗的点正好落回原来的位置、看起来不动，只有亮点在跑，两格之间叠一帧渐变；连续转的每帧转一点。
  圆心先按规划给的位置，再找「转一格之后和自己最重合」的位置；圆盘外面一个像素都不动。最后一帧再转一格就是第一帧，首尾天然接得上。
  只调一次生图接口，转出 GIF 不到 2 秒。
- **数据图表按数据画准。** 生图模型画柱状图、折线图、饼图时只会画「像图表的东西」：柱子高矮和数值对不上，刻度乱标，
  数字写错。图里要放数据图表时，应用让模型只画一张在那个位置留出空白面板的图（白板、卡片、屏幕、纸面），坐标轴、刻度、
  网格、柱子、折线、扇形、数值标注和图例都由程序按数据画上去，再从最终文件里量回来核对：先量出刻度线拟合「数值→像素」，
  再检查每根柱子的端点、每个数据点、每个扇形的边界，偏差超过约 1.5 像素就不交付。柱状图和条形图的数值轴一律从 0 起，
  刻度取整齐的间隔，饼图的百分比按最大余数法分配、加起来正好 100%，数值标注只补零不四舍五入。规划只抄你给的数，
  比例、合计由程序算；图里有数在你的原话里找不到，交付时会列出来请你核对。模型画的面板常常和规划的位置对不齐、
  或者带着窗光的明暗渐变，图表跟着整块面板画；面板上画了别的东西就打回重画。之后改数、加减类目、换图表类型、
  换颜色，直接在保存下来的底图上重画，一两秒就好，不调用生图接口。
- **有限次修正。** 最多 5 轮；连续 2 轮没改善就换改法；连续 3 轮提前收手；
  内容安全审核拒绝会立即停止，不再重试。
- **扛得住短暂的服务故障。** 生图、上传、下载遇到网关错误（HTTP 429、5xx）或连接断开时，会等一会儿再试两次，
  等待逐次拉长；评审回合失败时等一会儿重评同一批图，不把它们扔掉重画。故障一直不恢复，或者中途出现 HTTP 401
  这类配置错误时，就停下来交付手上已有的最好的图，并在图下面写明是中途停下的。
- **跨图对比。** 所有图出完后拼一张并排对比图，判断「同一个主体是不是同一个东西」。只报告，不自动重画。
- **交付验收报告。** 每次交付都带一份 `report.json`：逐图判定、每次生图的 `request_id`、成本，
  以及它没能验证的部分。

## 环境要求

- MiniMax Code 3.1.6 或更高版本（本应用声明了 `toolAccess` 与 `agentAccess`）。
- 一个 H3-Image 接口地址和 API Key。

## 安装

1. 把整个目录（含隐藏的 `.minimax-plugin`）复制到 MiniMax Code 的插件目录，目录名为
   `h3-image-executor/`（默认是 `~/.minimax/plugins/h3-image-executor/`），也就是清单最终位于
   `~/.minimax/plugins/h3-image-executor/.minimax-plugin/plugin.json`。
2. 重启 MiniMax Code，确认插件已启用。
3. 对 Agent 说「打开 H3-Image-Executor」，或从插件列表里打开。

## 配置接口

本应用**不内置任何默认接口地址**。在配置之前，侧边栏底部的引擎状态会显示「未配置生图接口」。

点击那行打开设置面板，填写：

| 字段 | 含义 |
| --- | --- |
| API Key | 你的 H3-Image Key，只会发往你配置的接口地址。 |
| 接口地址 | H3-Image 接口的基础地址，必须以 `https://` 开头。 |

Key 写入 Host 为本插件创建的私有 `dataDir` 下的 `settings.json`，权限 `0600`。它不会写进包体、
不会打进日志。保存下来的 Key 不会回传给页面：页面只能拿到前 6 位和 Key 长度。

也可以在 shell 里导出后重启 MiniMax Code：

```sh
export MINIMAX_API_KEY="..."
export MINIMAX_BASE_URL="https://..."
```

`MCODE_API_KEY` 也会被当作 Key 读取；进程环境变量里两个都有时以 `MINIMAX_API_KEY` 为准。
`H3_IMAGE_MODEL` 可以覆盖模型名，默认是 `MiniMax-H3-Image`。

解析顺序是：页面里保存的配置 → 进程环境变量 → `~/.zshrc` / `~/.zprofile` /
`~/.bash_profile` / `~/.profile`。**页面优先**，你在页面上明确填过的值不会被别处遗留的环境变量覆盖。

## 使用

在输入框里写下你要的图，回车发送。应用会跑完整条链路并交付图片和报告。几点值得知道：

- **默认输出 4K。** 除非你指定画幅，否则由规划决定。
- **每次生图都会显示 `request_id`**，在过程时间线上是一个 `req …` 小标签，点一下复制完整值；
  反馈问题时请附上它。
- **失败的图会说清原因。** 接口报错（包括内容安全审核拒绝）会带着原始报文出现在交付区，
  而不是一句没有下文的「0 张」。
- **可以在同一会话里追问。** 再发一条消息是在已交付的图上继续改，而不是从头再来。
- **参考图不对就直说。** 追问「参考图找的不对，重新找」会给还没有参考图、或者你说不对的主体重新检索，
  用找到的图重画；重新检索什么都没找到时，面板会如实说明，不会白画一遍。你手上有对的图时，直接上传仍然最可靠。
- **二维码。** 直接说码里放什么，例如「二维码链接至 https://www.minimax.cn/」。内容必须出现在你自己的话里：
  规划给的内容在原话里逐字找不到时，不贴码，改为在交付里问你。每张交付图会标「二维码可扫」（已换成真码并扫码通过）、
  「装饰码」（没给内容）或「二维码没换成」（附原因）。只补或只换内容的追问（如「二维码换成 https://…」）
  几秒钟就在交付图上换好，不调用生图接口，也不重新评审。
- **程序排的字。** 文字由程序排上去的图会标「文字由程序排入」，下面写着字体和排法；「文字没排上」表示预留给文字的
  地方没留空，并写明原因。要改就在同一会话里说，例如「字换成宋体」「字大一点」「加上标点」。书法作品（古文、诗词、
  对联、手卷）默认不写标点，和古人的写法一样；你说要标点，就缩小写在字旁。排上去的是字体不是手写：同一个字每次
  出现都长得一样，排在整齐的格子里。旧版本留下的会话里，要改模型写的长段文字时，会先让模型把字擦掉，再由程序排字。
- **GIF 动图。** 说要 GIF、动图或会动的表情包，有图就附上。应用先画出来的参考图标「GIF 参考图 · 待确认」，下面写着计划的
  各帧；点「生成 GIF」开始出帧，或者直接说要改哪里，先改参考图。卡片上有倒计时：1 分钟内没有任何回应，就按默认确认、
  自动开始出帧，这一轮在对话里标着「按默认确认自动开始」；不想自动开始就点「先别生成」。等待期间应用重启，倒计时重新
  计满 1 分钟；应用关了很久再打开，不会替你开始。交付的 GIF 标「GIF · N 帧」，下面是带编号的帧条，
  GIF 和参考图都能下载。同一会话里可以接着说「慢一点」「第 3 帧重画」「去掉最后一帧」「在第 2 帧后面加一帧眨眼」「只播一遍」
  「别要渐变」：调快慢、顺序、尺寸、是否循环、帧和帧之间渐变还是直接切换，或者删帧，几秒钟重新合成，不调生图；重画或加帧
  只画那一帧。要改主体本身（换颜色、换衣服），会先改参考图，再等你确认一次。GIF 默认长边 768 像素（最大 1024），
  所有帧共用一套 255 色的调色板。
- **转圈的 GIF。** 说要加载圈、转圈的图标就行，例如「做一个十二个点的加载圈 GIF，512×512」。交付卡片上放的是 GIF，标「GIF · N 帧」，
  下面是一圈里的各帧，GIF 和原图都能下载。接着可以说「转快一点」「反过来转」「一圈 8 格」「连续转」：几秒钟重新转，不调生图；
  要改样子（换颜色、换点的形状）照常改图，改完按新图重新转。一张已经画好的图，说「让它转起来」也行。
- **组图拼 GIF。** 交付的组图上接着说「把这组图变成 GIF」，一两分钟后交付卡片上放的是 GIF，标「GIF · N 格」，下面是带格子编号的帧条
  （从上到下、从左到右数，补的过渡格标「格子号+」），GIF 和组图都能下载。不想等、也不要过渡格，就说「直接拼，不要补帧」。
  接着可以说「每格停久一点」「最后一格多停一会儿」「来回播」「去掉第 3 格」「换个顺序」「加渐变」「切换时弹一下」，几秒钟重新拼，
  不调生图（去掉一格后多出来的那一步会补一格过渡）；有几步没补上过渡格时卡片上会写，说「更顺一点」再补一次；
  说「第 3 格改成生气」会照常改组图，改完按新的组图重新补过渡格、重新拼。
  图里没有分格时会照实说切不出格子，不会重画；白底贴纸这种格子之间什么都没有的图，说「按 2 行 3 列切」就按等分切。
- **数据图表。** 要图里有柱状图、条形图、折线图、面积图、饼图或环形图时，把数直接写在需求里（「2021 到 2025 年营业额
  分别是 86、120、158、203、245 万元」），没给数而图表又是重点时，应用会先问你要。交付图标「图表核对通过」，
  有数在你的原话里找不到时标「图表 · 请核对数据」；「交付详情」里列出图表用的全部数据。同一会话里可以接着说
  「2024 年改成 280」「换成折线图」「加一年 2026 年 300」「颜色换成蓝色」「去掉图表」：只改图表时不重新生图。
  一张图最多 3 张图表，每张最多 24 个类目、6 个系列。
- **历史在侧边栏。** 每条可以重跑或删除。重跑开一个新会话，只带原来的需求和你当时手动上传的图；检索来的参考图、
  程序画的角色基准图和 GIF 参考图、上一次的结果都不带。删除是把会话移进 `dataDir` 下的 `sessions/.trash/`，不是抹掉。
  应用从不清空这个目录，要释放磁盘空间请自己删除里面的内容。
- **停止任务。** 「停止」按钮会中止这个会话的 Agent 轮次，并在下一步结束任务。已经发给接口的
  生图请求仍会跑完，但之后不会再启动新的步骤。
- **也可以直接在聊天里说。** 启用插件后，在会话里说「画一张…」会把需求交给本应用，
  而不是在聊天里另生成一张图；你点名要用别的工具、或者说不想用这个面板时除外。随包发布的
  `h3-image-executor` Skill 会引导 Agent 用 `?prompt=…&auto=1` 打开面板，页面自己填好输入框并提交。

### 启动参数

面板会从自己的 query string 里读这些参数。Agent 就是靠它把需求递进来的，你也可以自己用来做深链：

| 参数 | 含义 |
| --- | --- |
| `prompt`（或 `q`） | 需求原文，逐字使用。 |
| `auto` | `1`（默认）填入并直接提交；`0` 只填入，等你自己按发送。 |
| `session` | 会话 ID，例如 `20261109-877482`。带上表示「接着调那一张」，不带表示开新的一张。 |
| `len` | 可选。发送方数出来的 `prompt` 字符数。和实际收到的对不上时，页面会提示需求可能在传输中损坏，但仍然提交。 |

页面读完就立刻把这些参数从地址栏抹掉，所以刷新不会把同一条需求再提交一遍。
如果还没配接口，需求会填进输入框但不会自动提交，输入框上方会说明原因。

## 数据与访问

**读取包体之外的文件**

- `~/.zshrc`、`~/.zprofile`、`~/.bash_profile`、`~/.profile`——按纯文本读取、从不执行，仅在你没有
  在页面里配置时，用于查找 `MINIMAX_API_KEY`、`MCODE_API_KEY` 和 `MINIMAX_BASE_URL`。这依赖 shell
  配置的文件布局，不属于任何已公布的契约。
- 你通过文件选择器挑的参考图。
- Agent 交给随包的 `h3-review`、`h3-qr`、`h3-gif` 命令行工具的图片和 GIF；以及 `h3-qr fix --content-file` 指定的、
  存放二维码内容的文本文件。
- 排字、画图表时读取的字体文件：原地只读，不复制、不修改、不上传。macOS 上是 `/System/Library/Fonts/STHeiti Medium.ttc`、
  `/System/Library/Fonts/STHeiti Light.ttc` 和 `/System/Library/Fonts/Supplemental/Songti.ttc`；Windows 上是
  `%WINDIR%\Fonts` 里的 `simkai.ttf`、`simsun.ttc`、`msyh.ttc` 和 `simhei.ttf`。每次排字都会读黑体和宋体的文件
  （排毛笔字也读），用来补所选字体里没有的字。文件不存在就跳过。

**写入的文件**

- 应用保存的所有内容都写在 Host 提供的 `dataDir` 下：`settings.json`（权限 `0600`）、
  `sessions/<id>/`（规划、图片、预览、参考图、评审拼图、交付物、报告、分享页 `share/index.html`
  及其内嵌大图的缓存 `share/large/`、`session.json`）、`refcache/`（下载的参考图，以及保留一天的下载失败记录）、`sessions/.trash/`
  （已删除的会话）。换二维码时，贴好真码的那份写在生成图旁边：`sessions/<id>/images/<候选号>-qr.jpg`
  （接口回 PNG 时是 `.png`），生成图本身原样保留。程序排字也一样：排好字的那份是
  `sessions/<id>/images/<候选号>-text.jpg`，模型画的无字底图留在旁边，之后改字都从它开始。程序画的图表同理：
  画好图表的那份是 `sessions/<id>/images/<候选号>-chart.jpg`，留白的底图留在旁边，之后改数都从它开始。GIF 的帧写在
  `sessions/<id>/images/<图号>F<n>-r<轮号>-g0.jpg`，512 像素的预览在 `previews/`；应用先画出来的参考图会按下一个 R 编号
  复制进 `sessions/<id>/refs/`；每一版交付目录里有 GIF（`<文件名>.gif`）、当作静态图的参考图（`<文件名>.jpg`）
  和帧条（`<文件名>-frames.png`）。组图拼的 GIF 写在 `sessions/<id>/images/<候选号>-panels.gif`，帧条是旁边的
  `<候选号>-panels-strip.png`；交付目录里是 GIF、组图本身和帧条。过渡格的候选组图写在 `sessions/<id>/images/<图号>T-r<n>-g<k>.jpg`，
  规划和评审用的看图材料写在 `sheets/`。程序转圈的 GIF 写在 `sessions/<id>/images/<候选号>-spin.gif`，
  帧条是 `<候选号>-spin-strip.png`；交付目录里是 GIF、原图和帧条。
- 两个 JSON 状态文件——`settings.json` 和 `sessions/<id>/session.json`——是原子写入：同目录临时
  文件再 `rename`。图片和 HTML 文件直接写。
- `dataDir` 之外只有四处会写文件：
  - 发布轮次（见「调用的工具」）会把分享页复制到本 Mini App 自己的 Agent 工作目录下的
    `h3-share-publish/index.html`，因为 `website_deploy` 只接受这个目录里的路径。每次发布都会覆盖它。
  - 随 `h3-image-review` Skill 发布的 `h3-review` 命令行工具，在 Agent 运行它时写 PNG 看图材料：
    `sheet` 写在输入图旁边，`refs` 和 `grid` 写在当前工作目录，或者写到 `-o` 指定的位置。
    应用自己从不运行它。
  - 随 `h3-image-qrcode` Skill 发布的 `h3-qr` 命令行工具，在 Agent 运行它时写：`fix` 把换好码的图写在输入图旁边，
    名为 `<原名>-qr.<扩展名>`（重名时加 `-2`、`-3`……，不覆盖已有文件），或写到 `-o` 指定的位置，永远不覆盖输入图本身；
    `make` 在当前工作目录写 `qr.png`（同样按序号避开重名），或写到 `-o` 指定的位置。`scan` 和 `locate` 不写文件。
    `fix` 没能让码扫得出时一个文件都不写。应用自己从不运行它。
  - 随 `h3-image-gif` Skill 发布的 `h3-gif` 命令行工具，在 Agent 运行它时写：`grid` 把 GIF 写在组图旁边（`<原名>.gif`），
    `slides` 写在第一张图旁边（`<原名>-slides.gif`），`spin` 写在图旁边（`<原名>-spin.gif`），`frames` 写在帧目录旁边（`<目录名>.gif`），重名时加 `-2`、`-3`……，
    或写到 `-o` 指定的位置；GIF 旁边再写一张帧拼图 `<GIF 名>-frames.png`（或 `--sheet` 指定的位置）。`split` 把各格写成
    `<原名>-panels/01.png`……（目录已存在就换一个），`check` 只在给了 `--sheet` 时写帧拼图。永远不覆盖输入文件；
    写出去的 GIF 读回来核对没通过时一个文件都不写。应用自己从不运行它。
- 页面在自己的浏览器存储里保存视图状态：侧边栏是否收起；以及每次页面被隐藏时记下的当前会话 ID、
  输入框里还没发出去的文字（最多 4000 字）和已选但未发送的参考图张数，这样 Host 重新加载页面后能恢复。

**网络**

- 你配置的 H3-Image 接口。它会收到你的 Key（作为 bearer token）、你的 prompt、你提供的和检索来的参考图，
  以及编辑时送回去的生成图：要改的那张、当作色彩基准的那张、GIF 的前一帧和补过渡帧时的前后两帧、补过渡格时的整张组图。
  没有默认值——就是你填的那个。
- 该接口返回的图片地址，应用会从那里下载图片。
- 参考图检索（见「调用的工具」）找到的图片地址，以及你在需求或追问里给出的图片地址：可能是任何第三方
  网站，`https` 或 `http` 都有。这些图都由应用自己下载、再上传给你的接口，从不让接口去取某个地址。
  规划轮次或追问轮次写出来、但你的原话里没有的地址一律不用。检索查询本身经由工具发出，不是本应用直接发出。

本应用拒绝从 `169.254.0.0/16`（云主机元数据服务所在的链路本地段）以及 `0.0.0.0` 这类通配地址
下载图片，跟随每一次重定向之前都会重新检查一遍地址。对检索工具给出的图片地址，还会拒绝 localhost
和私有段（`10.*`、`172.16-31.*`、`192.168.*`、`100.64-127.*`、`fc00::/7`），包括解析到这些地址的
域名：第三方的检索结果不应该让应用去读你自己网络里的东西。对你的接口返回的图片地址、以及你自己给出的
图片地址，私有段和 localhost 仍然允许，因为你的接口本身可能就在内网。每次下载都有上限：
参考图 25 MB，生成图 100 MB。

**启动的进程**

只有剪贴板命令，没有别的。每一条都是参数固定、不拼 shell、2 秒超时、输出有上限。

- **读**——MiniMax Code 禁止 Mini App 页面读剪贴板，所以设置面板里的「剪贴板」按钮会让 Node 服务
  调一次本机的粘贴命令：macOS 是 `pbpaste`，Windows 是
  `powershell.exe -NoProfile -NonInteractive -Command Get-Clipboard`，Linux 是 `wl-paste` 或
  `xclip`，上限 8 KB。读到的内容只用于回填输入框：不写日志、不落盘，而且只有「像 Key」或
  「像 `https://` 接口地址」时才会回传给页面。
- **写**——页面先用浏览器剪贴板复制（`navigator.clipboard.writeText`，不行再用
  `document.execCommand('copy')`）。这两条都要求面板处于聚焦状态，而面板经常没有焦点，所以 Node 服务
  也可以调本机的复制命令：macOS 是 `pbcopy`，Windows 是
  `powershell.exe -NoProfile -NonInteractive -Command Set-Clipboard -Value ([Console]::In.ReadToEnd())`，
  Linux 是 `wl-copy` 或 `xclip`，上限 2 KB。它只在两种情况下执行：你发起的一次发布完成时自动执行
  一次，把新的公开链接放进剪贴板；以及会话已有公开链接、你点「分享」而页面没能复制时。Node 服务只接受
  单行的 `https://<name>.space.mcode.cn` 地址，其余一律拒绝——所以这个接口没法被当成「往你剪贴板里
  写任意内容」的后门。

加载时、定时轮询时、保存时都不会启动任何进程，除此之外不会启动任何子进程。

**Agent 轮次**

本应用声明 `agentAccess: ["session.run"]`，会运行 Agent 轮次来做规划、评审和修正。这些轮次运行在
你 MiniMax Code 会话所配置的模型服务上，因此你的 prompt 原文、参考图以及生成出来的图本身都会送到
该模型服务，用于规划、评审、修正和选优；筛选参考图候选时，检索工具给出的候选标题和网站名也会一起送过去；
规划和追问轮次还会看到本机排字用的字体名（例如「宋体-简」「马善政毛笔楷书」）。这些轮次可以读写文件、执行 shell 命令、调用 MCP 工具，
均受你的权限规则约束。每一个工具权限请求都会展示在页面上由你决定，包括下面「调用的工具」里说的
发布轮次发起的 `website_deploy` 请求；应用从不替你放行。它自己只会拒绝发布轮次发起的其他工具请求。
如果你在插件详情里关闭了 Agent 权限（`session.run`），任务会停下，页面会说明去哪里重新打开。
它没有声明 `session.read`，读不到你的其他会话。

**调用的工具**

本应用声明 `toolAccess: ["call"]`，只调用一个工具：已安装工具里第一个名字包含 `search_images`
的工具。在测试环境里它是 `connector__matrix__search_images`，即 `matrix` Connector 的
`search_images` 工具。它收到的是规划写的检索词（主体名，或者画风、版式这类说法；搜不到时还有规划给的另一种说法），
以及一句说明要找什么样的图，返回图片地址。一次规划或追问里搜几次受检索预算约束（最多 16 次，搜图和判定候选合计；
服务报错时的自动重试不计）。每次调用
都走你的权限规则；规则为「询问」时，应用会在第一次检索前弹出 Host 的确认框，请你始终允许这一个工具。
如果你在插件详情里关闭了工具调用（`tool:call`），任务会在没有检索参考图的情况下继续，页面会说明原因。

「发布公开链接」按钮是另一回事，值得单独说清楚：它会起一个 Agent 轮次，这轮唯一的任务是调用
Host 的 `website_deploy` 工具，把自包含分享页发布到一个公开的 `https://<name>.space.mcode.cn`
地址，**任何拿到链接的人都能打开**。页面里包含：你的需求和追问、你上传的或应用在网上找到的参考图、
其余检索结果的缩略图、规划、所有候选图和交付图的缩小版、每张交付图一份长边 2048px 的大图（点开时显示）、
评审拼图、应用发给模型的完整提示词和模型的回复，以及带 `request_id` 和成本的执行记录，还有每一张交付的 GIF 原文件。
大图总量上限 4 MB，GIF 总量上限 3 MB；超出的交付图点开时仍是预览大小，超出的 GIF 显示成它的参考图。你点了这个按钮、并且在页面上对出现的 `website_deploy`
请求点了「允许一次」之后，才会真正发布。按钮下面常驻一行提示，说明任何拿到链接的人都能打开，以及页面包含
哪些内容。写盘前，本机路径会被替换成占位符：会话目录和插件的 `dataDir` 保留其后的相对部分，用户
主目录下的其他路径、以及 `/Users/` 或 `X:\Users\` 下的路径整段替换。发布轮次的其他工具请求一律
拒绝；如果它发起提问，整轮直接中断。

**随包发布的 Skill**

  工具、或者说不想用这个面板时除外。你问起某次跑完的任务时，它会让 Agent 去读本插件数据目录下的
  `sessions/<id>/session.json`。Skill 并不知道 MiniMax Code 把这个目录放在哪里，所以找到它依赖未公开的
  目录布局。
- `h3-image-review` 告诉 Agent 在你要它亲自看生成图时，怎么运行随包的 `h3-review` 工具（见「写入的文件」）。
- `h3-image-qrcode` 告诉 Agent 在你要它把图里的码换成能扫的、检查一个码能不能扫、或单独生成一张二维码时，
  怎么运行随包的 `h3-qr` 工具（见「写入的文件」）：内容从你的原话里逐字照抄，你没说就先问；只有工具自己扫码
  通过才能说码能用。面板里出的图，它会让 Agent 回到面板会话里改。
- `h3-image-gif` 告诉 Agent 在你要它把一张分格组图、几张单独的图，或者它自己写程序画的一组帧做成 GIF，以及检查一个 GIF 时，
  怎么运行随包的 `h3-gif` 工具（见「写入的文件」）：只有工具读回来核对通过才能说做好了。面板里出的组图，它会让 Agent 回到面板会话里做。

二维码的生成和验证全部在应用的 Node 进程和上面这两个工具里完成：不发网络请求、不启动进程、不跑 Agent 轮次、
不调用工具。码里放的内容是规划的一部分，所以规划轮次和你需求的其余部分一样能看到它。程序排字也一样：读字体、
排字都在 Node 进程里完成，评审轮次看到的排好字的图和别的候选没有区别。组图切格、拼 GIF 也全在 Node 进程和 `h3-gif` 里完成，
不发网络请求、不调生图接口。

**设备使用**

不使用麦克风、摄像头和系统通知，未声明任何 `deviceAccess`。
不读取你当前所在的 MiniMax Code 页面，也不读取浏览器历史。页面只在你点击复制控件时（`req …` 标签，
或已有链接时的「分享」）以及你发起的发布完成后写一次剪贴板；上面那些剪贴板命令跑在 Node 服务里。
应用只看得见它自己的面板。

## 已知限制

- 角色设定图能改善一致性，但不保证。设定图与故事图之间姿势或画幅差异大时仍会漂移。
- 内容安全审核拒绝是确定性的，所以应用在第一次被拒时就停下，不再重试。请修改需求本身后重新发送。
- 参考图检索依赖检索工具，可用性随它而定。工具拒绝或检索失败时，这个主体就没有检索到的参考图，
  请自己上传一张。检索预算用完时，排在后面的项不搜、或者判不完，交付说明里会写明。
- WebP 格式、以及算术编码、无损、CMYK 的 JPEG 参考图候选解不开。它们会被跳过，时间线会写明原因，不算作「不符合要求」。
- 二维码：程序靠三个角的回字形定位方块找码，模型画的码被遮挡、倾斜过大、做成艺术化图案或没有定位方块时找不到。
  这时会带着更严格的要求重画，不经评审最多两次；之后走正常的评审修正循环，所有候选的码都没换成时，交付最好的那张，
  标「二维码没换成」并附原因。只生成和验证正色码（深色码印在浅底上），反色码多数手机扫不了。每张图最多 3 枚码。
  换码时整张图会按质量 93 重新编码一次 JPEG（PNG 仍是 PNG）。验证用的是软件解码器（jsQR），从多种裁切范围、
  以及每个模块约 2 像素的缩小图读最终文件；这是很强的信号，但不保证每一部手机都能扫出印出来的码。
- 程序排字：空白检测找的是颜色均匀的区域，纹理很强的载体（木纹、砖墙、花纹布料）可能被判成没留空；不经评审重画两次之后
  走正常的评审修正循环，交付时标「文字没排上」。让模型擦掉它自己写的字时，常会留下旧笔画的痕迹，要多调几次生图才能
  拿到干净的底图。字是平着、正着排在一个矩形里的，放在倾斜或弯曲的招牌上会像贴上去的。
  两款毛笔字体随包发布；宋体和黑体用 macOS 和 Windows 的系统字体，楷体只在 Windows 上用系统字体（macOS 的楷体要按需下载，
  所以改用随包的毛笔楷书），Linux 上所有书体都退回随包的毛笔字体。CFF 轮廓的字体（多数 `.otf`）读不了。
  所有可用字体里都没有的字，会退回让模型直接写。排字时整张图会按质量 93 重新编码一次 JPEG（PNG 仍是 PNG）。
  一字两色只能按左、右、上、下切一刀：半包围、全包围的字（这、国、同）切不出偏旁，整字用一种颜色。
  规划后的文字核对只对照你原话引号里的内容，没加引号的文字不核对。
- GIF 是关键帧动画，不是视频。每一帧在前一帧上接着改，帧要一帧一帧地画，8 帧约 2 分钟；连着改十几次，人物可能一点点走样，
  靠每次都附上参考图、合成时锁回背景和色调压着，在动的部位里小细节（围巾的褶皱、毛发纹理、五官）仍会帧与帧略有不同。
  单独重画中间某一帧之后，后面的帧还是接着原来那一帧画的，衔接靠程序量出跨度后补的过渡帧。渐变只补在差得不多的两帧之间，
  差得多的地方直接切换。镜头运动、背景变化做不了：
  整幅都在变的帧不会锁背景。WebP 的参考图用不了，应用解不开这种格式。GIF 最多 256 色：带柔和渐变的照片类
  帧会有一点色带（这类帧会加有序抖动，平涂的插画不加）。
- 程序转圈只能绕垂直于画面的轴转（平面上转），硬币翻面、地球自转这种立体的转动做不了。转的是圆心周围一整块圆盘，
  里面的背景跟着一起转，所以背景要是纯色或者从圆心往外的渐变（规划会这样要求）；圆盘里有别的图案，转起来看得出来。
  一格一格跳的要求点或辐条等距：模型画得不匀时，暗的点每帧会抖一两个像素。连续转的不找圆心，用规划给的位置。
- 组图拼 GIF 是一格一格地切换，不是连贯的动作：要眨眼、挥手这类顺滑的动作，用上面那种按参考图出帧的 GIF。
  程序靠分隔线或留白找格子；格子直接挨着画、没画分隔线时按等分切。格子之间什么都没有（白底贴纸）、格子歪斜或
  互相压着（漫画的出格分镜）时找不准，要你说几行几列，按等分切；不等分又没有分隔线的排法切不准。
  各格按中上部（主体的头和脸）做平移对齐，最多挪格子宽高的 4%：每格里主体大小不一样、或者头不在中上部时对不齐，
  模型每格画的背景位置也会差一两个像素。
  过渡格是模型画的，会画错（手的位置不对、照抄了前后格），程序和评审挑不出能用的那一步就直接切换；人物画法和关键格总会差一点，
  过渡格的背景用它所在那一格的像素，所以到下一格时背景（比如屏幕上的 K 线）还是一下子换过去。补满过渡格的 GIF 帧数翻倍，
  文件大约大一倍。不补过渡格时，表情、手一下子换成下一格的样子；加渐变的话，两格差得多时叠出来是两只半透明的手。
  说了要「切换时弹一下」才会加：每格多一整帧，GIF 大约大一倍，整幅画面每次切换会先放大再落回。
- 数据图表是程序画的平面图表：线条和字是规整的印刷风格，不是手绘，也不会跟着面板的透视变形，所以面板要正对镜头
  （规划会这样要求）。支持柱状、条形、折线、面积、饼图、环形图和堆叠柱状，不支持散点、雷达、地图和表格。
  同一张图表里的数值标注统一保留同样的小数位（2185.8 和 3191.43 在一起时写成 2185.80）。数从你的原话里找不到时照样画，
  只在交付时提醒你核对；你给的是图片里的表格时，程序没法核对原文。
