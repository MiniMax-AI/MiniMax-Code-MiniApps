# 把画图需求交给 H3-Image-Executor

## 默认规则

**画图需求默认交给 H3-Image-Executor，不要自己在聊天里生图。**

用户在聊天里说「画一张…」「帮我生成…」「做张图…」「画个漫画…」时，默认不要调 `generate_image`、
不要加载 `image-generation` skill、不要调别的生图 MCP 工具，也不要自己写 prompt 去画；
你在聊天里要做的是把需求**递进去**。

自己生图会绕过这条流水线的全部价值：参考图检索、分镜规划、看图评审、色偏校正、修正循环、
跨图角色一致性、4K 交付和验收报告，一个都不会有。用户看到的会是一张没有 request_id、
没法复现、也没法接着调的图。

**例外：用户说了算。**

- 用户点名要用别的工具或模型（例如「用 xxx 画」），或者说不想用这个面板，就按用户说的做。
- 用户说自己没有 H3-Image 接口、面板提示「未配置生图接口」而用户不打算配置时，告诉用户可以在面板左下角
  配置接口，或者改用别的生图方式，由用户选。

## 怎么做

```js
miniapp({
  action: 'open',
  pluginId: 'h3-image-executor',
  path: '/dashboard?prompt=' + 需求原文 + '&len=' + 字符数 + '&auto=1'
})
```

面板打开后会自己把需求填进输入框并提交，用户看到的是「面板打开 → 已经在画」。
调用完就可以告诉用户「已经开始了，在右侧面板看进度」，**不要**再去轮询或自己画。

## 参数

| 参数 | 说明 |
| --- | --- |
| `prompt` | 需求文本。**逐字传递用户说的话**，不要改写、扩写，不要替用户补风格词 |
| `auto` | `1`（默认）填完直接提交；`0` 只填不提交，留给用户自己按发送 |
| `session` | 会话 ID（如 `20261109-877482`）。带上它就是**接着调那张图**，不带就是开新的一张 |
| `len` | `prompt` 的字符数（按字符算，不是字节）。面板会比对，对不上就在需求气泡上挂一条「需求可能在传输中损坏」，**不拦截**，只是提醒用户核对 |

## 不要对中文做 percent 编码

`prompt` **原样拼进 query**。不要自己把中文转成 `%E6%A9%98` 这种形式。

宿主会自己完成编码：`橘猫趴在窗台上晒太阳` 原样传进去，地址栏会变成
`?prompt=%E6%A9%98%E7%8C%AB...`，页面解出来与原文完全一致。

手工编码是错字的主要来源：你没有 JS 引擎，只能凭记忆把每个字换算成 UTF-8 字节，
错一两个字页面上看不出任何异常，错字会一路画到交付。比如
`猫`(U+732B，应为 `E7 8C AB`) 被写成 `E7 8C AA` = `猪`(U+732A)，
需求就变成「橘猪趴在窗台上晒太阳」，整张图白画。

只有这 4 个 ASCII 字符必须编码——宿主不会替你转，它们会破坏 query 结构：

| 字符 | 写成 | 不编码的后果 |
| --- | --- | --- |
| `&` | `%26` | 后半截变成另一个参数，需求被截断 |
| `+` | `%2B` | 被解成空格 |
| `#` | `%23` | 变成 fragment，工具直接拒绝 |
| `%` | `%25` | 畸形百分号转义，工具直接拒绝 |

`=` 不用管，值里的 `=` 能完整保留。

## 三条纪律

1. **需求原文逐字传。** 流水线第一步就是规划，用户的话会被拆成 prompt；你先「帮忙润色」一遍，
   等于把用户的原意换掉，而且事后没人知道改了哪。缺信息（尺寸、张数、风格）就问用户，
   不要自己替他决定。

2. **可以先查资料，但只把需求说清楚，不要把资料塞进 prompt。**
   比如「把今天的天气预报画成一张四格漫画」：可以先 `web_search` 弄清今天的天气，
   然后传一句绘画需求进去（说明画什么、什么形式）。
   不要把新闻正文、检索结果整段拼进 `prompt`——那是规划器该消化的输入格式，不是给人写的。

3. **一次 `open` 就是一次作画。** 用户要四张图，流水线会自己拆成四张并锁定角色一致性，
   不要手动开四个会话，也不要分四次调用。

## 需求里有二维码

生图模型画不出能扫的二维码。流水线的做法是：规划时把码里要放的内容从需求里逐字记下，出图后由程序找到模型画的码，
换成真码并扫码验证，扫不出就打回重画。所以码里放什么必须写在需求里。

- **用户说了码里放什么**（链接、文字、号码）：照常原样传，不用额外处理。
- **用户要码但没说放什么**：先问一句「二维码里要放什么链接或文字？」。拿到回答后，把用户的原话接在需求后面一起传，
  例如 `…电子名片。二维码内容：https://www.minimax.cn/`，不要改写、不要补全。
  用户说「先不放」「随便」：照常传，交付时会注明这是扫不出的装饰码。
- **不要自己编网址**，也不要把你查到的网址当成用户的内容塞进去。

不是这个面板出的图（用户自己给的图、别的工具画的图）要换码，用 `h3-image-qrcode` skill 里的 `h3-qr fix`。

## 需求里有大段文字

生图模型写不好长段文字、竖排和毛笔书法，会编字、漏句。流水线遇到这类文字（一段 24 字以上、竖排、书法作品等），
会让模型只画一张载体留空的底图，再由程序用字体把规划从需求里抄下的文字逐字排上去。所以：

- **文字照原样传**，一个字都不要改：不要缩写、不要「纠正」异体字、不要替用户补标点或删标点。
- 用户只说了篇名（「写一幅《静夜思》」）时照原话传，规划会自己写出全文；用户给了全文就连全文一起传。
- 书法作品默认不写标点（古代书法本来不写）。用户明确要标点的，把用户的原话一起传进去。
- 排上去的是字体，不是手写。用户问「是不是真的毛笔写的」时如实说：底图是模型画的，字是程序用毛笔字体排的。

## 要做 GIF 动图

用户要 GIF、动图、会动的表情包时也交给这个面板，不要自己拼帧、不要改用别的工具（面板以外的图见本节最后一条）。流水线先定一张参考图，
第一帧从参考图改，后面每帧接着前一帧改一小步，一共 4–16 个关键帧（帧数按动作幅度定，一步跨太大的地方程序会补过渡帧），由程序拼成循环 GIF：

- **用户手上有图**（「把这张猫做成挥手的 GIF」）：告诉他在面板里上传这张图，需求照原话传。各帧直接照这张图改。
- **用户没给图**：照原话传。面板会先画一张参考图交付，标「GIF 参考图 · 待确认」，用户点「生成 GIF」或回复确认后才出帧；
  卡片上有 1 分钟的倒计时：用户这段时间里没有任何回应，就按默认确认、自动开始出帧；用户点「先别生成」就停住，
  等他确认。用户想先改参考图，就带 `session` 把修改要求递进去（这也会取消倒计时）。
- 动作写清楚就行（「先眨眼，再挥手」），帧数和每帧时长由规划定；用户点名了帧数、速度、尺寸就原话一起传。
- 这是关键帧动画，不是视频：合成时程序会把背景锁住、相邻两帧之间补渐变，但镜头运动、背景变化做不了。
  用户要的是这类效果时如实说。用户想要一下一下跳的效果（像素风、定格、卡点），原话传就行，面板会改成直接切换。
- **绕中心转的 GIF**（加载圈、转圈的图标、齿轮、风车）：照原话传。面板只画一张图，由程序按圆心转出各帧，不会丢帧、首尾接得上，
  一次生图就交付 GIF；用户说「转快一点」「反过来转」「一圈 8 格」也带 `session` 递进去，不重新生图。硬币翻面、地球自转这种
  立体的转动做不了，用户要的是这种时如实说。
- **组图做成的 GIF**（表情从笑到哭、分步动作）：照原话传。规划可能让面板先画一张分格组图，评审通过后切格拼成 GIF，
  相邻两格之间各补一格过渡（一起生成、从候选里挑），组图和 GIF 一起交付。已经交付的组图，用户说「把这组图变成 GIF」时
  带 `session` 递进去（见下一节）：组图不重画，补过渡格要一次生图，一两分钟。用户说不要补帧、直接拼，也原话一起传。
- 不是这个面板出的组图（用户自己给的、别的工具画的）要拼 GIF，几张单独的图要按顺序拼成 GIF（面板只拼一张分格组图，
  这种情况它会在交付说明里请你来拼），或者你要写程序在图上画会动的东西，用 `h3-image-gif` skill 里的 `h3-gif`。

## 图里要放数据图表

用户要柱状图、条形图、折线图、面积图、饼图、环形图，或者信息图、海报里带一张数据图表时，也交给这个面板，
不要自己算比例、不要自己写好图表的描述再传。面板让模型画一张留出空白面板的底图，图表由程序按数据画上去，
画完从成品里把柱高、数据点、扇形角度量回来核对：

- **数要写在原话里。** 用户说了数就原样一起传（「2021 到 2025 年营业额分别是 86、120、158、203、245 万元」）；
  用户只说「画一张销售额增长的图」没给数，先问他要，不要替他编。百分比、合计、增长率由程序算，不用先算好。
- 用户点名了图表类型、颜色、位置、单位就原话一起传；没点名由规划定。
- 交付里有数在用户原话里找不到时，面板会列出来请用户核对，如实转告，不要替他确认。
- 程序画的是规整的平面图表，不是手绘，也不跟着面板的透视变形；散点、雷达、地图、表格画不了，用户要的是这类时如实说。

## 用户接着提修改

用户在聊天里说「把背景换成夜景」「再加一张」时，如果指的是刚才那张图，带上 `session`：

```js
miniapp({
  action: 'open',
  pluginId: 'h3-image-executor',
  path: '/dashboard?session=' + sessionId + '&prompt=' + 修改要求 + '&len=' + 字符数 + '&auto=1'
})
```

不带 `session` 会开成一张全新的图，用户会以为上一张白画了。

用户补一句二维码内容（例如「二维码链接到 https://…」「码换成我的微信号 xxx」）也一样带 `session` 递进去，
`prompt` 照样逐字传用户的话：面板会直接在上一版交付图上把码换成真码、扫码验证，不重新生图，几秒钟就好。

用户说参考图不对、要重新找（例如「参考图找的不对，重新找」「吉祥物不像，换张参考图」）也带 `session` 原话递进去：
面板会给没有参考图、或者用户说不对的主体重新检索，用找到的图重画；什么都没找到时会如实说明，不会白画一遍。
不要自己去网上找图、也不要把网址塞进 `prompt`——面板只用用户自己给的地址，别的地址一律忽略。
用户手上有对的图时，告诉他可以在面板里直接上传参考图，这是最可靠的办法。

用户要改图里的字（例如「字换成宋体」「字大一点」「加上标点」「第三句改成……」）也带 `session` 原话递进去：
字是程序排的，面板直接在无字底图上重排，不重新生图，几秒钟就好；字是模型画的，面板会先让模型把字擦掉，再由程序排。

用户要改图表（例如「2024 年改成 280」「换成折线图」「加一年 2026 年 300」「颜色换成蓝色」「去掉图表」）也带 `session`
原话递进去：图表是程序画的，面板直接在留白的底图上按新数据重画，不重新生图，一两秒就好。

用户要调 GIF（例如「慢一点」「第 3 帧重画」「去掉最后一帧」「在第 2 帧后面加一帧眨眼」「只播一遍」「别要渐变」）也带 `session`
原话递进去：调快慢、顺序、尺寸、循环、渐变还是直接切换和删帧只是重新合成，不重新生图；重画、加帧只画那几帧；
改主体本身（换颜色、换衣服）会先改参考图，再请用户确认一次。

用户要把交付的组图变成 GIF（「把这组图变成 GIF」「做成动图」），或者调组图拼的 GIF（「每格停久一点」「来回播」「去掉第 3 格」
「加渐变」「切换时弹一下」「更顺一点」「不要补帧」），也带 `session` 原话递进去：变成 GIF 时组图不重画、补过渡格要一次生图；
只调节奏时几秒钟重新拼，不重新生图；要改某一格的画面（「第 3 格改成生气」）会照常改组图，改完重补过渡格、重新拼。
图里没有分格时面板会如实说切不出格子，不会重画。

## 交付之后

面板里会出验收报告和每张图的 `request_id`。用户问「画得怎么样」「用的什么 prompt」
「为什么这张失败了」，去读会话目录：

```
<插件数据目录>/sessions/<sessionId>/session.json
```

- `turns[].events[]` —— 每个阶段的进展，带 `stage` 和 `requestId`
- `images[]` —— 每张图的 `id` / `status` / `failReason` / `requestId`
- `turns[].delivery.items[].qr` —— 每张交付图的二维码状况：`real`（已换成真码、扫码通过）/ `decorative`（没给内容的装饰码）/
  `unverified`（规划给的内容在用户原话里找不到，没贴）/ `failed`（给了内容但没换成，`note` 里是原因）
- `turns[].delivery.items[].text` —— 程序排字的状况：`status` 是 `overlay`（已排入）/ `failed`（没排上，`note` 里是原因），
  `font` 是用的字体，`items[].layout` 是排法（几列几行、字高、标点怎么处理，有没有和同类文字统一字号、首行空几格、
  几个脚注符号排成上标、上方画没画分隔线、规划位置不空时往上或往下挪了多少）；`baseFile` 是不带字的底图。
  一张图最多排 16 段文字，超出的段落写在交付说明里。两段字排到一起时这张候选不交付（原因写「两段文字排到了一起」）。
  `images[].rounds[].action.type` 为 `text` 且带 `textPatches` 的轮次，是评审让程序在某张候选的底图上挪字重排，没有调生图接口
- `images[].rounds[].candidates[].checks[]` —— 程序和评审逐项的结论。`H-color` 是偏红判定（需求要的主色就是黄、红、橙、
  画面又几乎没有中性色时写「交给评审看」，不判偏红）；`H-white` 只在需求写明白纸、白底时出现，`text` 里是白色区域实测的
  RGB 和通道差（4 级以上判不通过）。`anchorId` 是这一轮编辑带的色彩基准图（第 2 张图，只对照颜色），`images[].colorAnchor`
  是这张图当前的色彩基准
- `refs[]` —— 参考图。`origin` 是 `user`（用户给的）/ `search`（检索来的）/ `generated`（角色基准图）；检索来的带 `use`
  （`subject` 主体外观 / `detail` 局部 / `style` 画风 / `layout` 版式 / `scene` 场景）和 `take`（要取它什么），
  生图时逐张写进 prompt。用户问「为什么搜了这么多图」「这张参考图拿来干嘛」，看这两个字段
- `refBudget` —— 规划给的检索预算：`limit` 上限、`used` 用了多少（`searches` 搜图、`gates` 判定）、`stopped` 是预算不够没搜的项。
  要不要检索由规划决定（`plan.ref_budget`，0 就是不搜）。用户问「为什么没去找参考图」「为什么只找了一半」，先看这里和 `plan.think`
- 程序排字里一个字两种颜色：`images[].spec.textOverlay.layers[].part`（`side` 偏旁在哪一侧、`color` 偏旁的颜色）；
  结果在候选的 `program.text.items[].part`：`ok` 是否分成了，`note` 是换了字体或没分成的原因。
  `images[].spec.readingProblems` 不为空时，表示规划的文字层按版面读不出用户引号里的这几处（规划已经改过一次），请用户核对
- `images[].spec.difficulty` —— 规划给这张图判的难度（`easy` / `normal` / `hard`，`difficultyReason` 是理由；空的表示规划没判，
  按规格推断）。它决定评审、修正、选优、追问编辑这些节点每次能调用几次工具：上限 = 必须打开的图 + 1 + 难度余量（1 / 2 / 4），
  撞过上限的节点下次再加 2。用户问「评审为什么被打断」「工具调用为什么是这个数」，看时间线节点详情里的「预算怎么定的」
- `turns[].delivery.items[].chart` —— 程序画图表的状况：`status` 是 `overlay`（已画入并核对通过）/ `failed`（没画上，`note` 里是原因）；
  `items[]` 每张图表一项：`typeLabel` 类型、`categories` 和 `series` 是图表用的全部数据、`verify.maxErrorPx` 是从成品量回来的最大偏差、
  `unverified` 是在用户原话里找不到的数（不为空时请用户核对）；`baseFile` 是留白的底图
- `turns[].delivery.items[].gif` —— GIF 的交付：`file` 是 GIF、`strip` 是帧条，`frames` 帧数（用户说「第几帧」就是这套编号）、
  `written` 是 GIF 里实际写了几帧（含渐变帧）、`inbetween` 是程序补的过渡帧有几帧、`cuts` 是两帧差得多没补渐变的有几处、`frameMs` 是规划写的每帧毫秒、`keyMs` 是实际每帧停多久（补了过渡帧、去掉没过评审的帧之后会变）、`durationMs` 整组时长、`loop` 是否循环、`transition` 是 `fade`（渐变）还是
  `cut`（直接切换）、`verify.ok` 是写出去之后读回来核对的结果；`items[]` 是逐帧的情况（`status` 为 `passed` / `unpassed`
  （没过评审，`skipped` 为 true 时没放进 GIF）/ `unreviewed` / `failed`（没画出来）/ `reference`（就是参考图），`mirrorOf` 不为 0 表示和第几帧用同一张图）。
  这一项的 `file` 是参考图本身，不是 GIF。`source` 为 `panels` 时是组图切格拼成的：`frames` 是放进 GIF 的格子数，
  `grid` 是几行几列和怎么切的（`method`：`line` 分隔线 / `gutter` 留白 / `free` 格子大小不一 / `even` 等分：格子之间没有清楚的分隔，或者按指定的行列），
  `order` 是播放顺序（格子编号从上到下、从左到右数），`keyMs`、`firstMs`、`lastMs` 是每格、第一格、最后一格停多久，
  `pingpong` 来回播，`bounce` 切换时弹不弹，`items[]` 是每格的行列和有没有放进 GIF（`inGif`）；这时 `file` 是组图本身。
  `images[].spec.panelGif` 是组图拼 GIF 的设定（`smooth` 为 false 时不补过渡格），`images[].panelGif` 是拼好的结果（`state` 为 `failed` 时 `error` 里是原因），
  `tweens` 是用上了几格过渡格、`tweenNote` 是没补上的原因。`images[].panelTweens.pairs[]` 是每一步过渡格：`from`、`to` 是哪两格，
  `text` 是过渡格规划写的样子，`status`（`passed` 评审挑的 / `unreviewed` 评审没跑成、按程序挑的 / `failed` 没补上 / `skipped` 不补），
  `candidateFile` 是用的哪张候选组图。
  `source` 为 `motion` 时是程序绕圆心转出来的：`steps` 一圈几格（0 是连续转）、`direction`（`cw` 顺时针 / `ccw` 逆时针）、
  `center` 程序最后用的圆心（画面宽高的比例）、`radius` 转的圆盘半径（短边的比例）、`keyMs` 每格多久、`durationMs` 一圈多久；
  这时 `file` 是原图。`images[].spec.motionGif` 是转法，`images[].motionGif` 是转好的结果
- `images[].animation.frames[]` 里 `status` 为 `unpassed` 的帧重画后还没过评审，没放进 GIF；它前后两帧之间 `inbetween` 为 true 的帧
  是按它原来的计划补的过渡帧
- `turns[].delivery.items[].animation` —— `state` 为 `awaiting_confirm` 时，这张是还在等用户确认的 GIF 参考图，
  `frames[]` 是计划出的各帧；`failed` 时 GIF 没做成，`error` 里是原因
- `autoConfirm` —— 参考图在倒计时：`deadline` 是到点自动开始的时间；`held` 为 true 表示用户点了「先别生成」；为 null 表示没在倒计时。
  `turns[].auto` 为 true 的那一轮是到点自动开始的，不是用户发的
- `status` —— `delivered` / `failed` / `running` / `cancelled`

不要把 `request_id` 截断或省略，用户要拿它去查账。

## 分享页与公开链接

每次交付都会自动把一份自包含的分享页落到：

```
<插件数据目录>/sessions/<sessionId>/share/index.html
```

**面板上的「发布公开链接」按钮会自己完成发布，你不需要再手动部署。**
用户点一下，按钮变「发布中…」，服务端起一个 Agent turn 去调 `website_deploy`。
这次调用**必须由用户在面板上点「允许一次」**才会执行：面板不会替用户放行，你也不要替用户回答。
好了之后链接会自动写进剪贴板——用户直接粘给别人就行。按钮下面常驻一行
「发布后任何拿到链接的人都能打开……」，写明了页面会公开哪些内容，这是用户点下去之前能看到的告知，不要把它删掉。

为什么能这么做：Mini App 的 `context` 只有 `agent / capabilities / hostConnector /
listen / logger / tool`，没有任何 drive / upload / storage 能力，页面和服务端自己做不到部署；
而 `website_deploy` 是 Host 的顶层控制工具，只下发给 Agent turn。所以唯一通路就是
`context.agent.run`（见 `miniapp/node/lib/publish.mjs`）。

**你不要主动替用户发布。** 用户没点按钮、也没明确说要公开链接时，不要自己调
`website_deploy`——公开发布是不可逆的外向动作。

### 什么时候还需要你介入

- **按钮发布失败**，用户让你排查。看会话事件流里 `stage=share` 的记录，失败原因会写在
  `shareError` 上（`publish_timeout` / `publish_no_url` / `publish_turn_failed` / `publish_asked_question` /
  `publish_aborted` / `publish_not_permitted`）。`publish_timeout` 最常见的原因是用户没在面板上点「允许一次」。
- **用户要重新发布或换站点。** 这时你自己调 `website_deploy`：

  ```bash
  mkdir -p <工作区>/h3-share/<sessionId>
  cp <插件数据目录>/sessions/<sessionId>/share/index.html <工作区>/h3-share/<sessionId>/
  ```

  `website_deploy` 只接受当前工作目录下的路径，直接传插件数据目录会被拒：
  `Cannot deploy: '...' is outside the workspace or invalid`。
  要更新已有站点就传 `node_id`，那会**整体替换**线上内容；不传就是新建一个站点。
  这两种结果不对称，先问用户要哪个。

  部署前核一遍这份 HTML 不含绝对路径、Key 和远程资源，三项都必须是 0：

  ```bash
  python3 -c "import re;s=open('<路径>/index.html',encoding='utf8',errors='replace').read();\
  print('abs',len(re.findall(r'/Users/|[A-Za-z]:\\\\\\\\Users',s)),'key',len(re.findall(r'sk-[A-Za-z0-9_-]{16,}',s)),\
  'remote',len(re.findall(r'https?://[a-z]',s)))"
  ```

  拿到 URL 后直接告诉用户。面板只显示它自己发布出去的链接，不会显示你手动部署的这一个。

分享页体积通常 3–7 MB：内嵌图统一走 JPEG，每张交付图另带一份长边 2048px 的大图（点开时显示，
总量上限 4 MB，超出的几张点开仍是预览大小）。仍然偏大时告诉用户「这批图太多，分享页偏大」，不要闷头重试。

## 需要人工复核生成图时

流水线自己会做看图评审。确实需要你亲自看图时，用 `h3-image-review` skill 里的
`h3-review` 命令产出固定版式的看图材料，不要自己写裁图、拼图、量像素的脚本。
